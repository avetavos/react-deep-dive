## The feature

The prompt was: *"Add a project dashboard: a search box backed by `use()`, a live metrics panel that refreshes when the selected project changes, a per-project detail panel with a notes field and a related-items list, and a refresh button wrapped in an error boundary."* The result below compiles, `tsc --noEmit` accepts every file, and every piece reuses a concurrent-React pattern this course's Concurrent & Suspense module already covers. Read it the way this module's [reading order](/react/en/reading-react/) recommends, adapted to a concurrent feature: hooks and their dependencies, effects vs events, and memo/compiler assumptions all show up here — just wearing `startTransition`, `use()`, and `useDeferredValue` instead of a plain `useEffect`. It has **6 real bugs**, none of which `tsc --noEmit` catches.

## The review walk

### Hooks & deps: `use()` called with a promise created fresh in render

`SearchResultsList` calls `fetchResults(query)` directly inside its render body.

<SpotTheBug code={`function SearchResultsList({ query }) {
  const results = use(fetchResults(query)); // a NEW promise every render
  return <ul>{results.map((r) => <li key={r.id}>{r.title}</li>)}</ul>;
}`}>
`use()` does not fetch or cache anything — it only reads whatever promise you hand it. Calling `fetchResults(query)` directly inside render builds a brand-new promise every single render, so the component either suspends indefinitely or refetches on every render, depending on timing. Proven in the probe: calling an uncached fetch twice with the same query produces **two** separate promises (two real network calls, by count), while the cached version returns the exact same promise reference both times.

```text
✓ as generated: calling the fetch directly in render builds a NEW promise every single call
✓ fixed: getResultsPromise caches by query — the SAME promise reference comes back

Test Files  1 passed (1)
     Tests  2 passed (2)
```

The fix caches the promise per query in a `Map`, so repeated renders (and repeated calls to the same query) all read the same, already-in-flight promise.
</SpotTheBug>

### Effects vs events: `startTransition(async)` losing priority after `await`

`handleChange` wraps the whole thing in `startTransition(async () => {...})`, then calls `setLastLogged(next)` after `await logSearchAnalytics(next)`.

<SpotTheBug code={`function handleChange(next) {
  startTransition(async () => {
    setQuery(next); // before the first await — covered
    await logSearchAnalytics(next);
    setLastLogged(next); // after the await — NOT re-wrapped
  });
}`}>
react.dev's `useTransition` troubleshooting section is explicit: only code **before** the first `await` is automatically part of the transition. `setLastLogged(next)` runs after the await and is not wrapped in its own `startTransition` — it silently reverts to a normal, urgent update. Proven with the exact mechanism a suspending update would hit: a `setState` that can cause a `Suspense` boundary to suspend, run the same way, with and without re-wrapping. Without re-wrapping, the boundary falls back to its loading UI immediately; with re-wrapping, React keeps the old content on screen while the new content loads in the background — exactly the guarantee `isPending` implies but this bug quietly breaks.

```text
✓ as generated: a setQuery after a bare await is NOT part of the transition — Suspense falls back immediately
✓ fixed: re-wrapping setQuery after await keeps it part of the transition — old content stays, no fallback

Test Files  1 passed (1)
     Tests  2 passed (2)
```

The fix is a second `startTransition(() => setLastLogged(next))` around the post-`await` call.
</SpotTheBug>

### Effects vs events: an effect fetch with no abort/race handling

`LiveMetrics` fetches a metric keyed by `projectId` inside a `useEffect`, with no cancellation.

<SpotTheBug code={`function LiveMetrics({ projectId }) {
  const [value, setValue] = useState(null);
  useEffect(() => {
    fetchMetric(projectId).then((result) => setValue(result));
  }, [projectId]);
  return <output>{value === null ? 'loading…' : value}</output>;
}`}>
If `projectId` changes quickly (clicking between projects), an earlier, slower request can resolve **after** a later, faster one and overwrite fresh state with stale data. Proven in the probe with a deliberately slow-then-fast pair (the slow request started FIRST, would resolve LAST): switching from the slow project to the fast one leaves the panel showing the **stale, slow** project's value.

```text
✓ as generated: a slow, stale response overwrites a newer, faster one
✓ fixed: LiveMetrics aborts the previous request, so the fast response always wins

Test Files  1 passed (1)
     Tests  2 passed (2)
```

The fix is an `AbortController`, created inside the effect and aborted from cleanup — the fixed version's own request for the previous `projectId` is cancelled the moment `projectId` changes again.
</SpotTheBug>

### Memo/compiler assumptions: `useDeferredValue` with no `initialValue`

`ItemDetail` defers `item.related` with `useDeferredValue(item.related)` — no second argument.

<SpotTheBug code={`const deferredRelated = useDeferredValue(item.related);`}>
Since React 19, `useDeferredValue` takes an optional `initialValue`, used only for the component's very first render. react.dev is explicit that **without** it, "the hook will not defer during the initial render" — the first render just gets the real value directly, with no deferred placeholder at all. Proven in the probe: rendering with no `initialValue` shows the real, full related-items list on the very first render (no deferral happened); rendering `useDeferredValue(related, [])` shows the empty placeholder on that same first render instead.

```text
✓ as generated: useDeferredValue(related) with no initialValue shows the REAL list on the first render
✓ fixed: ItemDetail(useDeferredValue(related, [])) shows the empty placeholder on the first render

Test Files  1 passed (1)
     Tests  2 passed (2)
```

The fix is `useDeferredValue(item.related, [])` — an explicit, cheap placeholder for the very first render, right after the key-reset remount below gives this component a fresh instance.
</SpotTheBug>

### Keys & identity: no key on a per-item subtree — a notes draft bleeds across items

`Dashboard` renders `<ItemDetail item={selected} />` with no `key` at all — switching `selectedId` re-renders the *same* `ItemDetail` instance in place.

<SpotTheBug code={`<ItemDetail item={selected} />`}>
`ItemDetail` owns local state (`notes`) that has nothing to do with `item.title`/`item.related` — React has no way to know it should reset. Without a `key`, switching from one item to another updates props on the SAME component instance; `notes` — a piece of state React has no reason to touch — simply carries over. Proven in the probe: type a draft note while viewing item A, switch to item B, and the SAME draft text is still sitting in the textarea, now attached to the wrong item.

```text
✓ as generated: without a key, switching items leaves the PREVIOUS notes draft on screen
✓ fixed: key={item.id} forces a clean remount — the notes draft resets per item

Test Files  1 passed (1)
     Tests  2 passed (2)
```

The fix is `key={selected.id}` on `ItemDetail` — the same reset-switch mechanism this course's Rendering & Reconciliation lesson proves: a changing key forces a clean unmount + remount, resetting every piece of that subtree's own state on purpose.
</SpotTheBug>

### Effects vs events: an error boundary does not catch an event-handler throw

`DangerZone`'s button calls `refreshDashboardData` directly as its `onClick`, relying on the `ErrorBoundary` wrapping it in `Dashboard`.

<SpotTheBug code={`export function DangerZone() {
  return <button onClick={refreshDashboardData}>Refresh data</button>;
}`}>
Error boundaries catch errors thrown **during rendering** (and in lifecycle methods) of the components below them — never inside an event handler, which is just a normal JS callback running outside React's render. Proven in the probe: clicking a button that throws directly inside `onClick`, wrapped in a real error boundary, never shows the boundary's fallback at all — the exception escapes all the way to the browser's own global `error` event (`message: "handler-boom"`), completely bypassing `getDerivedStateFromError`.

```text
✓ as generated: a throw inside an onClick handler is NOT caught by the error boundary
✓ fixed: DangerZone catches the same throw itself with try/catch and shows a local error

Test Files  1 passed (1)
     Tests  2 passed (2)
```

The fix handles the throw where it actually happens: a plain `try/catch` inside the event handler itself, with local error state — an error boundary was never going to see it.
</SpotTheBug>

```ts
    setTimeout(() => resolve([{ id: `${query}-1`, title: `Result for "${query}"` }]), 5);
  });
}

  return Promise.resolve(void query);
}

const cache = new Map<string, Promise<SearchResult[]>>();

// FIX (use() reading a stable promise): cached per query, never a fresh
// promise on every render — use() only reads a promise, it never caches one.
export function getResultsPromise(query: string): Promise<SearchResult[]> {
  if (!query) return Promise.resolve([]);
  if (!cache.has(query)) cache.set(query, fetchResults(query));
  return cache.get(query)!;
}
```

```tsx
// src/dashboard/LiveMetrics.tsx
import { useEffect, useState } from 'react';

// A tiny simulated backend, deliberately slower for one id, so a real
// out-of-order response race can be reproduced deterministically in a test.
export function fetchMetric(projectId: string, signal: AbortSignal): Promise<number> {
  const delayMs = projectId === 'slow' ? 30 : 5;
  return new Promise((resolve, reject) => {
    const id = setTimeout(() => resolve(projectId === 'slow' ? 111 : 222), delayMs);
    signal.addEventListener('abort', () => {
      clearTimeout(id);
      reject(new DOMException('aborted', 'AbortError'));
    });
  });
}

// FIX (effect fetch race): an AbortController cancels the in-flight request
// for the PREVIOUS projectId, so a slow, stale response can never overwrite
// a newer, faster one.
export function LiveMetrics({ projectId }: { projectId: string }) {
  const [value, setValue] = useState<number | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    setValue(null);
    fetchMetric(projectId, controller.signal)
      .then((result) => setValue(result))
      .catch((err: Error) => {
        if (err.name !== 'AbortError') throw err;
      });
    return () => controller.abort();
  }, [projectId]);

  return <output data-testid="metric">{value === null ? 'loading…' : value}</output>;
}
```

## What changed and why

| # | Bug | Category | Fix |
|---|---|---|---|
| 1 | `use(fetchResults(query))` — a new promise every render | Hooks & deps | Cache the promise per query in a `Map` |
| 2 | `setLastLogged(next)` issued after `await` inside `startTransition(async () => {...})` | Effects vs events | Re-wrap the post-await call in its own `startTransition` |
| 3 | Effect fetch keyed by `projectId` with no cancellation | Effects vs events | `AbortController`, aborted from cleanup |
| 4 | `useDeferredValue(item.related)` — no `initialValue` | Memo/compiler assumptions | `useDeferredValue(item.related, [])` |
| 5 | `<ItemDetail item={selected} />` — no `key` | Keys & identity | `key={selected.id}` forces a clean remount per item |
| 6 | `onClick={refreshDashboardData}` — relies on an `ErrorBoundary` above it | Effects vs events | `try/catch` inside the event handler itself |

## Mental Model

Concurrent React features (`startTransition`, `use()`, `useDeferredValue`) are still built on the same primitives this course's Hooks module covers — a dependency array, a reference comparison, a component instance's own state — they just apply those primitives to *when* and *in what order* work happens, not only to *what* gets rendered. Every bug in this review is one of those same familiar failure modes (a stale value, a reference that changes when it shouldn't, state that should have reset) wearing a concurrent-API's clothes.

## Common Misconceptions

- **"`startTransition(async () => {...})` marks the whole callback low-priority."** Only the code before the first `await` is automatically covered — proven above, twice (with and without re-wrapping) against a real Suspense boundary.
- **"An error boundary around a component protects everything that component does."** It protects render-time errors from that component's subtree — not a click handler, not a rejected promise handled outside `use()`, and not the boundary's own code.
- **"If a component's props didn't change, its internal state is safe."** `ItemDetail`'s `notes` state has nothing to do with `item.related`/`item.title` at all — the parent has to opt in to a reset with `key`, or state that should be per-item just carries over silently.
