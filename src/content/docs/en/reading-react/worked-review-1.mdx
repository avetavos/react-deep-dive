## The feature

The prompt was: *"Build a todo app with add/toggle, a filter bar (all/active/completed), an undo history, an auto-clear timer that sweeps completed items after a delay, and a stats panel showing the active count and percent done."* The result below is the kind of first draft an AI assistant hands back — it compiles, `tsc --noEmit` accepts every file, and every piece looks like something you have already seen in this course's Hooks and Foundations modules. Read it the way the [reading order](/react/en/reading-react/) in this module's index recommends: hooks and their dependencies first, then keys and identity, then state ownership, then effects vs events, then memo pairing. It has **6 real bugs**, none of which `tsc --noEmit` catches.

```tsx
// src/todos/TodoApp.tsx — as generated
import { useState } from 'react';
import { useAutoClear } from './useAutoClear';
import TodoList from './TodoList';
import StatsPanel from './StatsPanel';
import type { Filter, Todo } from './types';

let nextId = 1;

function TodoApp() {
  const [todos, setTodos] = useState<Todo[]>([]);
  const [filter, setFilter] = useState<Filter>('all');
  const [history, setHistory] = useState<Todo[][]>([]);

  function addTodo(text: string) {
    setHistory((h) => [...h, todos]);
    setTodos((prev) => [...prev, { id: String(nextId++), text, done: false }]);
  }

  function toggleTodo(id: string) {
    setHistory((h) => [...h, todos]);
    setTodos((prev) => prev.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
  }

  function markAllDone() {
    todos.forEach((t) => { t.done = true; });
    setTodos(todos);
  }

  function undo() {
    setHistory((h) => {
      if (h.length === 0) return h;
      setTodos(h[h.length - 1]);
      return h.slice(0, -1);
    });
  }

  function clearIds(ids: string[]) {
    setTodos((prev) => prev.filter((t) => !ids.includes(t.id)));
  }

  useAutoClear(todos, clearIds);

  const visible = todos.filter((t) => {
    if (filter === 'active') return !t.done;
    if (filter === 'completed') return t.done;
    return true;
  });

  return (
    <div>
      <button onClick={() => addTodo(`Task ${nextId}`)}>Add</button>
      <button onClick={markAllDone}>Mark all done</button>
      <button onClick={undo} disabled={history.length === 0}>Undo</button>
      <div role="group">
        {(['all', 'active', 'completed'] as const).map((f) => (
          <button key={f} aria-pressed={filter === f} onClick={() => setFilter(f)}>{f}</button>
        ))}
      </div>
      <TodoList todos={visible} onToggle={toggleTodo} />
      <StatsPanel todos={todos} />
    </div>
  );
}

export default TodoApp;
```

## The review walk

### Hooks and their dependencies: a stale closure in the auto-clear interval

`useAutoClear` sets up `setInterval` inside a `useEffect` with an **empty** dependency array — so the effect (and the closure the interval callback captures) runs exactly once, on mount.

<SpotTheBug code={`export function useAutoClear(todos, onClear) {
  const [delayMs, setDelayMs] = useState(3000);
  useEffect(() => {
    const id = setInterval(() => {
      const stale = todos.filter((t) => t.done).map((t) => t.id);
      if (stale.length) onClear(stale);
    }, delayMs);
    return () => clearInterval(id);
  }, []); // empty deps
  return { delayMs, setDelayMs };
}`}>
The interval callback closes over the **mount-time** `todos` — an empty array, since the app starts with no todos. Adding a done todo later never recreates the interval (the dependency array is empty), so the callback keeps checking that original, empty array forever. Proven in the probe: render the hook, add a done todo, advance the fake timer past `delayMs`, and `onClear` is never called at all.

```text
✓ useAutoClearBad: the interval keeps reading the EMPTY todos array from mount, forever

Test Files  1 passed (1)
     Tests  1 passed (1)
```

The fix is `useEffectEvent` (React 19.2): extract the non-reactive read into an Effect Event, which always sees the latest `todos`/`onClear` without ever becoming a dependency of the effect itself.
</SpotTheBug>

### Hooks and their dependencies: `useMemo` on a trivial value, with an empty dependency array

`StatsPanel`'s `activeCount` is a one-line filter over `todos` — cheap enough that it never needed `useMemo` at all. The AI-generated draft reaches for `useMemo` anyway, and gets the dependency array wrong the way `useMemo`/`useCallback` almost always get it wrong when added out of habit rather than need.

<SpotTheBug code={`const activeCount = useMemo(() => todos.filter((t) => !t.done).length, []);`}>
An empty dependency array means this memo is computed once, on the first render, and then frozen — `activeCount` never updates again no matter how `todos` changes afterward. Proven in the probe: render with one active todo (`activeCount` shows `1`), add a second active todo, and `activeCount` is still stuck at `1`.

```text
✓ StatsPanelBad: useMemo([]) freezes activeCount at its first-render value

Test Files  1 passed (1)
     Tests  1 passed (1)
```

The fix here isn't a corrected dependency array — it's deleting the `useMemo` entirely. `todos.filter(...).length` is cheap enough to compute during every render; wrapping it in `useMemo` added a second place for a dependency array to go stale, for zero performance benefit.
</SpotTheBug>

### Keys and identity: the array index as the list key

`TodoList` uses the item's position in the array (`i`) as `key`, not a stable id from the data.

<SpotTheBug code={`function TodoList({ todos, onToggle }) {
  return (
    <ul>
      {todos.map((todo, i) => (
        <TodoItem key={i} todo={todo} style={{ opacity: todo.done ? 0.5 : 1 }} onToggle={onToggle} />
      ))}
    </ul>
  );
}`}>
As long as the list never reorders or has an item prepended, this looks completely fine. The moment an item is inserted at the front — exactly what "Undo" and reordering by filter can do — React matches the OLD row's internal state to whatever item now happens to sit at the same index, not to the item it was originally attached to. Proven in the probe with a stand-in checkbox row (an uncontrolled `checked` state, the same shape this bug takes in real forms): check the first row, prepend a new item, and the checked state stays on **position 0** — now a different item entirely.

```text
✓ key={index}: checking the first row, then prepending an item, bleeds the check to the WRONG row
✓ key={todo.id}: the same reorder keeps the checked state on the correct row

Test Files  1 passed (1)
     Tests  2 passed (2)
```

The fix is `key={todo.id}` — a stable id from the data itself, never the row's current position in the array.
</SpotTheBug>

### State ownership: mutating `todos` before calling `setTodos`

`markAllDone` really does update every todo's `done` field — but it mutates the array in place first.

<SpotTheBug code={`function markAllDone() {
  todos.forEach((t) => { t.done = true; });
  setTodos(todos);
}`}>
Every item really is mutated (`done: true` in memory), but `setTodos(todos)` passes the **identical array reference** it already had. React's `Object.is` bail-out check sees no change and skips the re-render — the UI keeps showing "not done" until some unrelated state change forces a render, at which point the already-mutated data suddenly appears. Proven in the probe: click "Mark all done" on a component built exactly this way, and the rendered list still reads "not done" — the DOM never updated at all.

```text
✓ MarkAllDoneBad: mutating then setting the SAME array reference leaves the UI stale
✓ TodoApp (fixed): markAllDone builds a new array of new objects, so the UI updates

Test Files  1 passed (1)
     Tests  2 passed (2)
```

The fix is `setTodos(todos.map((t) => ({ ...t, done: true })))` — a new array of new objects, so `Object.is` correctly sees a change.
</SpotTheBug>

### Effects vs events: syncing a derived stat through an effect

`percentDone` is entirely computable from `todos.length` and `activeCount` — it needs no state and no effect of its own.

<SpotTheBug code={`const [percentDone, setPercentDone] = useState(0);
useEffect(() => {
  setPercentDone(todos.length === 0 ? 0 : Math.round(((todos.length - activeCount) / todos.length) * 100));
}, [todos, activeCount]);`}>
Syncing a derived value with an effect adds an extra render on every change: the effect fires *after* the render that changed `todos`, with the OLD `percentDone` still showing, then a second render fires with the synced value. It also gives `percentDone` a second place to drift out of sync with the data it's derived from. Nothing here throws or warns — the number is eventually correct, just one render late every time.

The fix is deriving it during render, no state and no effect at all: `const percentDone = todos.length === 0 ? 0 : Math.round(((todos.length - activeCount) / todos.length) * 100)`.
</SpotTheBug>

### Memo pairing: an inline style object defeats `React.memo`

`TodoItem` is wrapped in `memo`, but `TodoList` builds a brand-new `{ opacity }` object literal on every render of the list — even when a specific todo's `done` value hasn't changed at all.

<SpotTheBug code={`<TodoItem key={i} todo={todo} style={{ opacity: todo.done ? 0.5 : 1 }} onToggle={onToggle} />`}>
`memo`'s shallow prop comparison always sees a "different" `style` prop, because it IS a different object every render — same shape, same values, different reference. `memo` never gets a chance to skip anything. Proven in the probe: three unrelated parent re-renders (nothing about the todo itself changed) produce three child re-renders with the inline-object version, and exactly one child render across the same three parent re-renders once `TodoItem` takes primitive props instead.

```text
✓ an inline style object defeats memo: 3 unrelated parent re-renders produce 3 child renders
✓ TodoItem (fixed): primitive props let memo skip 2 of 3 unrelated parent re-renders

Test Files  1 passed (1)
     Tests  2 passed (2)
```

The fix is restructuring `TodoItem` to accept `text`/`done` as separate primitive props — primitives compare correctly by value, with no object reference to accidentally rebuild.
</SpotTheBug>

```ts
// src/todos/useAutoClear.ts
import { useEffect, useEffectEvent, useState } from 'react';
import type { Todo } from './types';

// FIX (stale closure): useEffectEvent always reads the LATEST todos/onClear
// without becoming a reactive dependency of the effect.
export function useAutoClear(todos: Todo[], onClear: (ids: string[]) => void) {
  const [delayMs, setDelayMs] = useState(3000);

  const tick = useEffectEvent(() => {
    const stale = todos.filter((t) => t.done).map((t) => t.id);
    if (stale.length) onClear(stale);
  });

  useEffect(() => {
    const id = setInterval(tick, delayMs);
    return () => clearInterval(id);
  }, [delayMs]); // only delayMs is genuinely reactive here

  return { delayMs, setDelayMs };
}
```

## What changed and why

| # | Bug | Category | Fix |
|---|---|---|---|
| 1 | `setInterval` effect with `[]` deps closes over the mount-time `todos` forever | Hooks & deps | `useEffectEvent` to read the latest `todos`/`onClear` without becoming a dependency |
| 2 | `useMemo(() => todos.filter(...).length, [])` freezes `activeCount` | Hooks & deps | Delete the `useMemo` — the computation is cheap enough to run every render |
| 3 | `key={i}` on a reorderable list | Keys & identity | `key={todo.id}` — a stable id from the data |
| 4 | `todos.forEach(t => t.done = true); setTodos(todos)` — same reference | State ownership | `setTodos(todos.map(t => ({ ...t, done: true })))` — a new array of new objects |
| 5 | `percentDone` synced through a `useEffect` | Effects vs events | Derive it during render — no state, no effect |
| 6 | An inline `{ opacity }` object passed to a `memo`-wrapped `TodoItem` | Memo pairing | Primitive `text`/`done` props — nothing for a fresh object reference to defeat |

## Mental Model

All six of these bugs compile clean and every one of them looks plausible reading the code once. None of them throw, none of them warn, and none of them are caught by `tsc --noEmit` — every single one is a claim about *behavior over time* (across a reorder, across a tick, across an unrelated re-render) that a single render can never disprove. That is exactly why this review ran a real Vite + React probe with fake timers, reorders, and render counters instead of reasoning about the code from the page.

## Common Misconceptions

- **"It compiles and the list renders correctly, so it's fine."** Every bug in this review produces a perfectly normal-looking list on the very first render. All six only show up on a *second* interaction: a tick, a reorder, an unrelated re-render, or a state change three renders later.
- **"`useMemo`/`useCallback` are free insurance — more memoization is always safer."** `useMemo([])` here didn't just waste the memoization; the wrong-forever dependency array turned a working computation into a frozen, stale one. Wrapping something in `useMemo` needs its OWN correctness check, not just a check on the thing being memoized.
- **"A `key` on every list item means the list identity is handled."** `key={i}` genuinely is a key — it just isn't a *stable* one. React's dev-mode "missing key" warning never fires here, because a key really is present.
