## The feature

The prompt was: *"Build a settings page: a name field using an Action, a notifications form with a pending indicator, a marketing opt-in toggle with optimistic UI, a theme toggle backed by an external store that can render on the server, a 'last saved' timestamp, and an avatar upload button."* The result below compiles, `tsc --noEmit` accepts every file **except one** (flagged below), and every piece reuses a React 19 API this course's React 19 module already covers. Read it the way this module's [reading order](/react/en/reading-react/) recommends: hooks and their dependencies (the one real type error lives there), then the server/client boundary (an external store rendering on the server), then state ownership (an optimistic setter called from the wrong place). It has **6 real bugs**.

## The review walk

### Hooks and their dependencies: `useRef()` with no initial value

`AvatarUpload` calls `useRef<HTMLInputElement>()` with zero arguments.

<SpotTheBug code={`function AvatarUpload() {
  const inputRef = useRef<HTMLInputElement>();
  return (
    <div>
      <button onClick={() => inputRef.current?.click()}>Choose avatar</button>
      <input ref={inputRef} type="file" style={{ display: 'none' }} />
    </div>
  );
}`}>
`@types/react@19` declares exactly three `useRef` overloads, and none of them takes zero arguments — the old "no argument, implicit `undefined`" habit from earlier type definitions no longer matches any of them. This is a real, current type error, verified against this exact React/TypeScript version:

```text
error TS2554: Expected 1 arguments, but got 0.
```

`tsc --noEmit` catches this one before the app ever ships — the only bug in this review that a plain type-check alone surfaces.
</SpotTheBug>

### The server/client boundary: `useSyncExternalStore` with no `getServerSnapshot`

`ThemeToggle` calls `useSyncExternalStore(subscribe, getSnapshot)` — two arguments, no third.

<SpotTheBug code={`export function ThemeToggle() {
  const current = useSyncExternalStore(subscribe, getSnapshot);
  return <button onClick={() => setTheme(current === 'light' ? 'dark' : 'light')}>Theme: {current}</button>;
}`}>
The third argument, `getServerSnapshot`, only matters once this can render on the server — but skipping it doesn't quietly fall back to something reasonable. react.dev is direct: "If you omit this argument, rendering the component on the server will throw an error." Proven in the probe with `renderToString`:

```text
Missing getServerSnapshot, which is required for server-rendered content. Will revert to client rendering.
```

The reason it must throw rather than silently degrade is hydration: the server has no `window` to call the client's `getSnapshot` with, and the client's first render must match the server's markup exactly, or React logs a mismatch. The fix is a third argument, `getServerSnapshot`, that returns a fixed value valid for the very first (server) render.
</SpotTheBug>

### State ownership: `useOptimistic`'s setter called outside a Transition

`MarketingOptIn`'s `handleToggle` calls `setOptimisticOptIn` directly in a plain event handler, then chains a `.then()` — no `startTransition` anywhere.

<SpotTheBug code={`function handleToggle() {
  setOptimisticOptIn(!optimisticOptIn);
  saveMarketingOptIn(!optimisticOptIn).then(() => setOptIn(!optIn));
}`}>
Per react.dev: *"The optimistic setter function must be called inside `startTransition` or within an Action. Calling the setter outside an Action will cause the optimistic state to revert immediately because there is no Transition holding it."* Proven in the probe with the real console message:

```text
An optimistic state update occurred outside a transition or action. To fix, move the update to an action, or wrap with startTransition.
```

The button briefly shows "Subscribed", then reverts — there is no Transition for React to "hold" the optimistic value in until the real state settles. The fix wraps the whole sequence in `startTransition(async () => {...})`.
</SpotTheBug>

### React 19 Actions: `useFormState` instead of `useActionState`

`NameForm` imports `useFormState` from `react-dom`.

<SpotTheBug code={`import { useFormState } from 'react-dom';

function NameForm() {
  const [state, formAction] = useFormState(updateNameAction, {});
  return (
    <form action={formAction}>
      <input name="name" />
      <button type="submit">Save</button>
      {state.error && <p role="alert">{state.error}</p>}
    </form>
  );
}`}>
`useFormState` still exists in `react-dom@19.2.8` — it is not a removed API — but it is the pre-rename name, and calling it prints a real, captured deprecation warning in this exact React version:

```text
ReactDOM.useFormState has been renamed to React.useActionState. Please update NameFormBad to use React.useActionState.
```

Beyond the warning, this component has no way to show a pending UI at all — `useFormState`'s return tuple has no third `isPending` element the way `useActionState`'s does. The fix is importing `useActionState` from `react` instead, which returns the same shape plus `isPending`.
</SpotTheBug>

### React 19 Actions: `useFormStatus` in the same component as `<form>`

`NotificationsForm` calls `useFormStatus()` directly, in the same function component that renders `<form>`.

<SpotTheBug code={`function NotificationsForm() {
  const [state, formAction] = useActionState(updateNotificationsAction, {});
  const { pending } = useFormStatus();
  return (
    <form action={formAction}>
      <button type="submit" disabled={pending}>{pending ? 'Saving…' : 'Save'}</button>
    </form>
  );
}`}>
`useFormStatus` reports the pending state of the nearest **ancestor** `<form>` — and the component that renders `<form>` is not its own descendant. This compiles and runs with zero errors or warnings; it just never works. Proven in the probe: clicking submit on a 20ms action and checking the button 5ms later, `pending` never becomes `true` here, even though the action is genuinely still in flight.

The fix moves `useFormStatus` into a separate child component rendered *inside* the `<form>` — exactly as this course's Server Components lesson first showed for the same hook.
</SpotTheBug>

### Effects vs events: `Date.now()` read during render

`LastSaved` reads `Date.now()` directly in its render body.

<SpotTheBug code={`function LastSaved() {
  return <p>Last saved: {Date.now()}</p>;
}`}>
`Date.now()` is, by definition, different every time it's called. A component rendered once on the server produces some HTML; the moment that same component executes *again* on the client to hydrate, it calls `Date.now()` a second time and gets a different value — a direct, textbook hydration mismatch. Proven in the probe (server rendered at one mocked timestamp, client hydrated at another, five seconds later):

```text
Hydration failed because the server rendered text didn't match the client. As a result this
tree will be regenerated on the client. This can happen if a SSR-ed Client Component used:

- A server/client branch `if (typeof window !== 'undefined')`.
- Variable input such as `Date.now()` or `Math.random()` which changes each time it's called.
- Date formatting in a user's locale which doesn't match the server.
- External changing data without sending a snapshot of it along with the HTML.
- Invalid HTML tag nesting.

It can also happen if the client has a browser extension installed which messes with the
HTML before React loaded.

https://react.dev/link/hydration-mismatch

  <LastSaved>
    <p>
+     1700000005000
-     1700000000000
```

React's own error message names `Date.now()` explicitly as a known cause. The fix computes the timestamp only on the client, inside an effect, so both the server render and the client's first render agree on a placeholder.
</SpotTheBug>

// src/settings/MarketingOptIn.tsx
import { startTransition, useOptimistic, useState } from 'react';

// A tiny simulated backend call — real, so a test can actually await it.
export async function saveMarketingOptIn(_v: boolean): Promise<void> {}

// FIX (useOptimistic outside an Action): the setter is wrapped in
// startTransition, so React has a Transition to "hold" the optimistic value
// in until the real state settles — otherwise it reverts immediately.
export function MarketingOptIn({ initial }: { initial: boolean }) {
  const [optIn, setOptIn] = useState(initial);
  const [optimisticOptIn, setOptimisticOptIn] = useOptimistic(optIn);

  function handleToggle() {
    startTransition(async () => {
      setOptimisticOptIn(!optimisticOptIn);
      await saveMarketingOptIn(!optimisticOptIn);
      setOptIn(!optIn);
    });
  }

  return <button onClick={handleToggle}>{optimisticOptIn ? 'Subscribed' : 'Subscribe'}</button>;
}

import { useEffect, useState, useSyncExternalStore } from 'react';

type Theme = 'light' | 'dark';
let theme: Theme = 'light';
const listeners = new Set<() => void>();

export function setTheme(next: Theme) {
  theme = next;
  listeners.forEach((l) => l());
}

function subscribe(listener: () => void) {
  listeners.add(listener);
  return () => listeners.delete(listener);
}

function getSnapshot(): Theme {
  return theme;
}

// FIX (missing getServerSnapshot): required the moment this store can render
// on the server — omitting it throws, specifically to protect the first
// hydration pass from disagreeing with the client.
function getServerSnapshot(): Theme {
  return 'light';
}

export function ThemeToggle() {
  const current = useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);
  return <button onClick={() => setTheme(current === 'light' ? 'dark' : 'light')}>Theme: {current}</button>;
}

// FIX (Date.now() in render -> hydration mismatch): the timestamp is read
// only on the client, inside an effect, after hydration has already
// reconciled — never during the render that both server and client run.
export function LastSaved() {
  const [time, setTime] = useState<number | null>(null);
  useEffect(() => {
    setTime(Date.now());
  }, []);
  return <p>{time === null ? 'Last saved: —' : `Last saved: ${time}`}</p>;
}

## What changed and why

| # | Bug | Category | Fix |
|---|---|---|---|
| 1 | `useRef<HTMLInputElement>()` — no argument | Hooks & deps | `useRef<HTMLInputElement>(null)` — React 19 types require it |
| 2 | `useSyncExternalStore(subscribe, getSnapshot)` — no `getServerSnapshot` | Server/client boundary | Add a third argument, `getServerSnapshot` |
| 3 | `setOptimisticOptIn(...)` called directly in an event handler | State ownership | Wrap the whole sequence in `startTransition(async () => {...})` |
| 4 | `useFormState` (from `react-dom`) — the pre-rename API | React 19 Actions | `useActionState` (from `react`) — same shape, plus `isPending` |
| 5 | `useFormStatus()` in the same component that renders `<form>` | React 19 Actions | Move it into a child `SubmitButton` rendered inside the form |
| 6 | `Date.now()` read directly in `LastSaved`'s render | Effects vs events | Compute it in an effect — client-only, after hydration |

## Mental Model

Three of these six bugs (`useRef()`, `getServerSnapshot`, `Date.now()`/hydration) are facts a tool can check for you — a real type error, a real thrown exception, a real captured mismatch message — the moment you actually run the right check (`tsc`, a server render, a hydration test). The other three (`useOptimistic` outside a Transition, `useFormState`'s missing `isPending`, `useFormStatus` misplaced) are API-shape facts: every one of them compiles and runs without crashing, and the only way to catch them is knowing what react.dev currently says an API guarantees — and checking the code actually keeps that guarantee.

## Common Misconceptions

- **"If it doesn't throw or warn, the React 19 API is being used correctly."** `useFormState` prints a real deprecation warning; `useOptimistic` outside a Transition prints a real warning too — but `useFormStatus` in the wrong component produces *nothing*, not even a hint, while just never working.
- **"`useSyncExternalStore`'s third argument is an optional nicety, like a default parameter."** It's required the moment this can render on the server — proven above, it throws rather than silently degrading, specifically to protect hydration.
- **"An optimistic UI library handles the Transition requirement for you."** `useOptimistic` is the primitive itself — nothing wraps the Transition automatically; the calling code has to.
