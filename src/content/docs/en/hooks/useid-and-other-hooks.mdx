## `useId`: SSR-safe unique ids

`useId` generates a unique, stable id string for one component instance — built specifically so it matches between server-rendered HTML and the client's hydration pass, which a hand-rolled counter or `Math.random()` cannot guarantee.

```jsx
import { useId } from 'react';

function PasswordField() {
  const passwordHintId = useId();
  return (
    <>
      <label>
        Password:
        <input type="password" aria-describedby={passwordHintId} />
      </label>
      <p id={passwordHintId}>The password should contain at least 18 characters</p>
    </>
  );
}
```

Hardcoding an id string works for exactly one instance of a component. Render `PasswordField` twice and a hardcoded id collides — invalid HTML (duplicate ids) and a broken `aria-describedby` association, because the browser's accessibility tree can only associate an id with one element.

```tsx
// src/__tests__/useid-duplicate-ids.test.tsx
import { useId } from 'react';
import { render, cleanup } from '@testing-library/react';
import { afterEach, expect, test } from 'vitest';

afterEach(cleanup);

// 🔴 Hardcoded id: every instance collides — invalid HTML (duplicate ids)
// and broken `aria-describedby` association for assistive tech.
function BadField() {
  return (
    <>
      <input aria-describedby="hint" />
      <p id="hint">Required</p>
    </>
  );
}

// ✅ useId: unique per component instance, stable across the component's life.
function GoodField() {
  const hintId = useId();
  return (
    <>
      <input aria-describedby={hintId} />
      <p id={hintId}>Required</p>
    </>
  );
}

test('hardcoded ids collide when a component renders more than once', () => {
  const { container } = render(
    <>
      <BadField />
      <BadField />
    </>,
  );
  const ids = [...container.querySelectorAll('p')].map((p) => p.id);
  expect(ids).toEqual(['hint', 'hint']); // duplicate — invalid HTML
});

test('useId gives each instance a distinct id', () => {
  const { container } = render(
    <>
      <GoodField />
      <GoodField />
    </>,
  );
  const ids = [...container.querySelectorAll('p')].map((p) => p.id);
  expect(new Set(ids).size).toBe(2); // no collision
});
```

Rendering **more than one independent React app on the same page**? Pass an `identifierPrefix` option to `createRoot`/`hydrateRoot` (and match it on the server's `renderToPipeableStream`) so ids from the two apps can never clash:

```js
const root1 = createRoot(document.getElementById('root1'), { identifierPrefix: 'app1-' });
const root2 = createRoot(document.getElementById('root2'), { identifierPrefix: 'app2-' });
```

**Don't** use `useId` to generate keys for a list — it's for accessibility attribute ids on a *fixed* number of elements per component instance, not per-item identity in a dynamic list (use each item's own stable data id for that).

## `useSyncExternalStore`: subscribing to state outside React

When state lives in a store that isn't React's own (a global variable, a browser API, a third-party library like Redux or Zustand's underlying subscription model), `useSyncExternalStore` is the hook that subscribes a component to it correctly — including a `getServerSnapshot` for SSR and protection against "tearing" (different components seeing different values from the same store during one render). This module's sibling lesson, [External Stores](/react/en/state-and-data/external-stores/), covers the full API, the tearing problem, and the classic selector pitfall in depth — this is the one-paragraph pointer, not a repeat of it.

## `useDeferredValue`: an `initialValue` for the first render (React 19)

`useDeferredValue` lets an expensive part of the UI lag behind an urgent update instead of blocking it. Since React 19, it takes a second argument, `initialValue`, used only for the component's very first render:

```jsx
import { useState, useDeferredValue } from 'react';

function SearchPage() {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query, ''); // '' only on first render
  // ...
}
```

Without `initialValue`, react.dev is explicit that the hook "will not defer during the initial render" — the very first render just gets `value` directly. With it, the first render gets `initialValue` instead, letting you show an immediate placeholder before any real query has been typed.

```tsx
// src/__tests__/useid-and-other-hooks.test.tsx (excerpt)
test('useDeferredValue(value, initialValue) uses initialValue on the FIRST render, not a deferred empty value', () => {
  const seenOnFirstRender: string[] = [];
  function Search({ query }: { query: string }) {
    const deferred = useDeferredValue(query, 'placeholder');
    seenOnFirstRender.push(deferred);
    return <output>{deferred}</output>;
  }
  render(<Search query="hello" />);
  // react.dev: "During the initial render, the returned deferred value will
  // be initialValue... If omitted, useDeferredValue will not defer during
  // the initial render." The first render shows the placeholder, not 'hello'.
  expect(seenOnFirstRender[0]).toBe('placeholder');
});
```

## `useDebugValue`: labeling a custom hook in DevTools

`useDebugValue` adds zero runtime behavior — it exists purely so React DevTools can show a readable label next to a custom hook's state instead of an opaque list of raw values:

```jsx
function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(true);
  // ...
  useDebugValue(isOnline ? 'Online' : 'Offline');
  return isOnline;
}
```

For a value that's expensive to format into a readable string, pass a second `format` function — React only calls it when DevTools is actually inspecting that hook, not on every render:

```jsx
useDebugValue(date, (d) => d.toDateString());
```

You'll only ever call this from inside a **custom** hook you're authoring — it has nothing to add inside an ordinary component.

## `useInsertionEffect`: CSS-in-JS authors only

`useInsertionEffect` fires **before** any layout effects, specifically so a CSS-in-JS library can inject `<style>` tags into the DOM before your component's `useLayoutEffect` calls try to read layout that depends on those styles being present. Proven below against `useLayoutEffect`:

```tsx
// src/__tests__/useid-and-other-hooks.test.tsx (excerpt)
test('useInsertionEffect fires before useLayoutEffect', () => {
  const log: string[] = [];
  function Widget() {
    useInsertionEffect(() => {
      log.push('insertion');
    });
    useLayoutEffect(() => {
      log.push('layout');
    });
    return null;
  }
  render(<Widget />);
  expect(log).toEqual(['insertion', 'layout']);
});
```

react.dev is direct about the audience: this hook is "primarily intended for CSS-in-JS library authors." It also comes with sharp caveats — you cannot update state from inside it, refs aren't attached yet when it runs, and it only ever runs on the client. Application code should reach for `useEffect` or `useLayoutEffect`; if you're not building a styling library, you almost certainly don't need `useInsertionEffect`.

## Mental Model

These five hooks aren't a random grab-bag — each one exists because a *specific* boundary needs crossing that the core hooks (`useState`, `useEffect`, `useRef`) weren't designed for: `useId` crosses the server/client boundary for identifier generation, `useSyncExternalStore` crosses the React/non-React state boundary, `useDeferredValue` crosses the urgent/non-urgent rendering priority boundary, `useInsertionEffect` crosses the styles-before-layout timing boundary, and `useDebugValue` crosses the runtime/DevTools-inspection boundary. If you're not standing at one of those five specific boundaries, you don't need the hook.

## Trade-offs

| Hook | Benefit | Cost |
| --- | --- | --- |
| `useId` | Guarantees no id collisions across instances or server/client hydration | One more hook call for something a hardcoded string "looks like" it could do |
| `useSyncExternalStore` | Correct, tear-free subscriptions to non-React state, with SSR support | More setup than reading a global variable directly (but that directness is exactly what causes tearing) |
| `useDeferredValue(value, initialValue)` | An immediate, sensible first paint instead of blocking on the real value | One more argument to remember; only matters for the very first render |
| `useInsertionEffect` | Styles land before layout effects read them | Only useful inside a styling library; wrong tool for ordinary app effects |

## Common Misconceptions

- **"A hardcoded id string is fine as long as I only render the component once."** True until someone reuses the component a second time on the same page — proven above, that's an immediate, invalid-HTML collision.
- **"`useId` is for React keys in a list."** It isn't — it's for accessibility attribute ids on a fixed set of elements per instance. List keys need per-item data identity, not `useId`.
- **"`useDeferredValue` without `initialValue` also defers on the first render."** react.dev states the opposite: with no `initialValue`, the hook does not defer on that first render at all — it only starts deferring on subsequent updates.
- **"`useInsertionEffect` is just an earlier `useEffect` for general use."** It's a narrow tool for style injection with real restrictions (no state updates, refs not yet attached) — reaching for it in ordinary application code is almost always the wrong call.

## Reading AI-generated code

When generated code uses one of these smaller hooks (or should, but doesn't), check for these before trusting it:

- Is an accessibility id (`aria-describedby`, `htmlFor`/`id` pairing) hardcoded as a string literal instead of generated with `useId`?
- Is `useId` being used to key a `.map()`-rendered list, instead of each item's own stable identifier?
- Does a component read from an external store (a module-level variable, `window`, a non-React library) directly during render instead of through `useSyncExternalStore`, risking tearing or a server/client mismatch?
- Is `useDeferredValue` used without considering whether the first render should show `initialValue` or the real value immediately?
- Is `useInsertionEffect` used for something other than style injection — a sign the author reached for it without understanding its narrow purpose and restrictions?
