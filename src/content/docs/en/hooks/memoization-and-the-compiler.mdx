## The problem memoization solves

Every render re-runs your component, which re-creates every value inside it — including objects, arrays, and functions. Those are **new references each time**, even if their contents are identical. Usually that's fine. It becomes a problem in two cases:

1. An **expensive calculation** runs on every render when its inputs didn't change.
2. A **new reference** (a function or object) passed to a memoized child breaks that child's memoization, causing needless re-renders.

The three memoization tools each address a piece of this:

| Tool | Caches | Use when |
|------|--------|----------|
| `useMemo(fn, deps)` | a **value** (the result of `fn`) | a calculation is expensive, or you need a stable object/array reference |
| `useCallback(fn, deps)` | a **function** (a stable reference) | you pass a callback to a memoized child (it's `useMemo` for functions) |
| `React.memo(Component)` | a **component's render** | a component re-renders with the same props and rendering it is costly |

```jsx
// Expensive calc, cached until inputs change:
const visibleTodos = useMemo(() => getFilteredTodos(todos, filter), [todos, filter]);

// Stable function reference so a memoized child does not re-render:
const handleSelect = useCallback((id) => setSelected(id), []);

// Skip re-render when props are shallowly equal:
const Row = React.memo(function Row({ item }) { /* ... */ });
```

### Proof: a new object reference defeats `React.memo`

```tsx
// src/__tests__/inline-object-breaks-memo.test.tsx
import { memo } from 'react';
import { render, cleanup } from '@testing-library/react';
import { afterEach, expect, test } from 'vitest';

afterEach(cleanup);

let renderCount = 0;

const Row = memo(function Row({ style }: { style: { color: string } }) {
  renderCount++;
  return <li style={{ color: style.color }}>row</li>;
});

test('a new object literal passed as a prop defeats React.memo — the child re-renders every time', () => {
  renderCount = 0;
  function Parent() {
    // 🔴 { color: 'red' } is a NEW object reference every render.
    return <Row style={{ color: 'red' }} />;
  }
  const { rerender } = render(<Parent />);
  expect(renderCount).toBe(1);
  rerender(<Parent />); // nothing Row's props actually changed
  rerender(<Parent />);
  expect(renderCount).toBe(3); // memo did nothing — re-rendered every time
});

test('a stable object reference lets React.memo actually skip re-renders', () => {
  renderCount = 0;
  const stableStyle = { color: 'red' };
  function Parent() {
    return <Row style={stableStyle} />;
  }
  const { rerender } = render(<Parent />);
  expect(renderCount).toBe(1);
  rerender(<Parent />);
  rerender(<Parent />);
  expect(renderCount).toBe(1); // same reference — memo skips the re-render
});
```

```text
✓ a stable object reference lets React.memo actually skip re-renders

```

## When memoization helps — and when it hurts

Memoization is not free: it costs memory and a comparison on every render. Applied everywhere "just in case," it makes code noisier and can be a net negative. It genuinely helps when:

- the cached calculation is measurably expensive, **or**
- you need a stable reference to keep a `React.memo` child (or an effect dependency) from re-running.

For cheap values — a string concat, a small `.filter` — computing during render is fine and clearer. Don't reach for `useMemo` reflexively.

## The React Compiler changes the calculus

React ships a **compiler** that automatically memoizes your components and values at build time — it inserts the equivalent of `useMemo`/`useCallback`/`memo` for you, precisely where they help, by analyzing your code. Its whole point is that **you should not need to memoize by hand**.

The practical guidance for React 19+ projects:

- **With the compiler enabled:** write plain, straightforward code. Don't scatter `useMemo`/`useCallback` — the compiler handles memoization for you, more correctly and more granularly than most hand-tuning. Your job is to keep components pure (the compiler relies on the Rules of Hooks and purity to be safe).
- **Without the compiler:** the manual tools above still apply — reach for them only at real, measured bottlenecks.

The direction of travel is clear: manual memoization is becoming an optimization of last resort rather than a default habit. Keep your components pure and let the compiler do the bookkeeping.

## Reading the compiler's real output

"The compiler auto-memoizes" is easy to accept on faith. Here it is made concrete: running `babel-plugin-react-compiler` (the actual package that powers the compiler, version `1.0.0` — the same major version react.dev's own release announcement calls stable) on a plain component with no manual memoization at all:

```jsx
// src/components/TodoList.jsx — the SOURCE, no useMemo/useCallback anywhere
function TodoList({ todos, filter, onSelect }) {
  const visibleTodos = todos.filter((t) => t.status === filter);
  const handleSelect = (id) => onSelect(id);
  return (
    <ul>
      {visibleTodos.map((t) => (
        <li key={t.id} onClick={() => handleSelect(t.id)}>
          {t.text}
        </li>
      ))}
    </ul>
  );
}
```

That's a **finer-grained** memoization graph than most developers would hand-write — the compiler tracks each sub-expression independently instead of memoizing the whole component with one `React.memo`.

## When manual memoization still matters

Even with the compiler enabled, there are real cases where `useMemo`/`useCallback`/`memo` still earn their keep:

- **The compiler didn't run on that code.** It only transforms components and hooks it can statically verify follow the Rules of React; code it can't safely analyze (or that lives outside the compiled directories/packages) is untouched and gets none of this for free.
- **A value needs to be stable for something *outside* React's render** — a `useEffect` dependency, a value handed to a non-React library that does its own reference-equality checks, or a module-level cache key.
- **You're not on the compiler yet.** Plenty of production code, and most of the ecosystem's libraries, still ship without it — the manual tools remain the only lever there.
- **Compatibility mode (`"use no memo"`).** The compiler lets a file or function opt out of compilation entirely when its code doesn't follow the Rules of React closely enough to memoize safely — in that escape hatch, you're back to manual memoization by design.

The rule of thumb hasn't inverted so much as narrowed: reach for manual memoization when you have a specific, measured reason the compiler can't cover, not as a default habit.

## Mental Model

The compiler is not "smarter `useMemo`" bolted on top of your code — it's a static analysis pass that rewrites your component into the same shape a very disciplined engineer would hand-write: one cache slot per sub-expression, each with its own dependency check. Manual `useMemo`/`useCallback` are the same idea, just coarser-grained and hand-maintained. Once you see the `$[n] !== value` pattern above, "the compiler auto-memoizes" stops being a slogan and becomes a mechanical fact you can read off the output.

## Trade-offs

| Choice | Benefit | Cost |
| --- | --- | --- |
| Let the compiler memoize | Finer-grained, automatically kept in sync with the code, no hand-maintained dependency arrays | Requires the toolchain to be set up, and only covers code it can statically verify is compiler-safe |
| Manual `useMemo`/`useCallback`/`memo` | Works everywhere, including outside compiled code and in older React versions | Coarser-grained, easy to under- or over-apply, dependency arrays must be kept in sync by hand |
| `"use no memo"` opt-out | Lets one file skip compilation when it doesn't follow the Rules of React | You're back to full manual responsibility for memoization in that file |

## Common Misconceptions

- **"The compiler makes `useMemo`/`useCallback` completely obsolete everywhere."** Only for code it actually compiles and can verify follows the Rules of React — untouched code, non-compiled packages, and effect-dependency stability needs still benefit from manual memoization.
- **"Compiler output means my component itself got memoized, like wrapping it in `React.memo`."** The output above shows per-*expression* memoization inside the function body, not a `React.memo` wrapper around the whole component — those are complementary, not the same mechanism.
- **"An inline object prop is only a minor inefficiency."** Proven above: it fully defeats `React.memo` — the child re-renders on literally every parent render, not "a little more than optimal."
- **"If I add `useMemo` everywhere, the compiler will just skip it."** The compiler preserves manually-written memoization it can verify is correct rather than blindly overriding it — so redundant hand-written `useMemo` isn't dangerous, but it also isn't buying you anything the compiler wasn't already going to do more precisely.

## Reading AI-generated code

When a generated component uses (or skips) memoization, check for these before trusting it:

- Is an object, array, or function literal created inline and passed as a prop to a component wrapped in `React.memo`? That silently defeats the memoization every time.
- Does the project actually have the React Compiler configured (check the build config / babel plugins), or is the code assuming compiler-level auto-memoization that isn't actually running?
- Is `useMemo`/`useCallback` wrapping a genuinely cheap computation "just in case," adding noise without measurable benefit?
- If a file has `"use no memo"` (or is otherwise excluded from compilation), does it still rely on manual memoization where it matters?
- Is a memoized value's dependency array missing something it reads — silently returning a stale cached value instead of recomputing?

  return <li style={style}>{style.label}</li>;
});

function List({ items }) {
  return (
    <ul>
      {items.map((item) => (
        <Row key={item.id} style={{ color: item.color, label: item.text }} />
      ))}
    </ul>
  );
}`}>
`Row` is wrapped in `React.memo`, but every call site builds a brand-new `{ color, label }` object literal on every render of `List` — so `Row`'s shallow prop comparison always sees a "different" `style` prop, even when `item.color`/`item.text` haven't changed at all. `React.memo` never gets a chance to skip anything. Proven in the probe with the same pattern: a memoized child fed a fresh inline object re-renders on every single parent render (3 renders in, 3 child renders out) — while the same child fed a stable object reference renders exactly once across 3 parent renders. The fix is to either build the style object with `useMemo` keyed on `item.color`/`item.text`, or restructure `Row` to accept `color`/`label` as separate primitive props instead of one object — primitives compare correctly by value, so no new-reference problem exists in the first place.
</SpotTheBug>

<Callout title="The one-line takeaway">
`useMemo` caches a **value**, `useCallback` caches a **function reference**, and `React.memo` skips a **child's re-render** when props are unchanged — a fresh object/array/function literal passed as a prop silently defeats all three. With the **React Compiler**, most of this happens automatically and at a finer grain than hand-written memoization — proven by reading its real output above — but manual memoization still matters for code the compiler doesn't touch, effect-dependency stability, and the `"use no memo"` escape hatch.
</Callout>
