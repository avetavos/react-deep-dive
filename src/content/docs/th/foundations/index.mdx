## แนวคิดในประโยคเดียว

**React render UI ของคุณเป็นฟังก์ชันของ state: `UI = f(state)`** คุณไม่ได้ update DOM เองตอนข้อมูลเปลี่ยน — คุณแค่บอกว่า UI *ควรหน้าตาเป็นอย่างไร* สำหรับ state ปัจจุบัน แล้ว React คิดต่อเองว่าต้องแก้ DOM น้อยที่สุดแค่ไหนเพื่อไปให้ถึงจุดนั้น

ทุกหัวข้อขั้นสูง — hooks, reconciliation, Suspense, compiler — ล้วนเป็นผลลัพธ์ของการเอาสมการเดียวนี้มาคิดอย่างจริงจัง เข้าใจ model ให้ถูก ที่เหลือก็ตามมาเอง

## โมดูลนี้ครอบคลุมอะไรบ้าง

| บทเรียน | สิ่งที่คุณจะได้เรียน |
|--------|-------------------|
| Why React & the model | declarative เทียบกับ imperative และ `UI = f(state)` |
| JSX & elements | JSX compile เป็นอะไร และ element จริง ๆ คืออะไร |
| Rendering & reconciliation | render/commit phase, virtual tree และ key |
| State snapshot & purity | state เป็น snapshot, immutability และทำไม render ถึง pure |

## เลนส์สำหรับทั้งคอร์ส

export const lensDiagram = `flowchart TB
  f["UI = f(state)\n(you describe, React updates)"] --> render["Re-render on state change\n(compute the new tree)"]
  pure["Render is pure\n(no side effects, same input same output)"] --> render
  render --> recon["Reconciliation\n(diff old vs new, patch the DOM)"]`;

- เพราะ **UI เป็นฟังก์ชันของ state** การเปลี่ยน state จึง trigger การ *re-render* — React รัน component ของคุณใหม่เพื่อคำนวณว่า UI ตอนนี้ควรเป็นอะไร
- เพราะ **render เป็น pure** React จึงเรียกมันเมื่อไรก็ได้ batch มันได้ restart มันได้ หรือรันซ้ำสองครั้ง (StrictMode) — ซึ่งเป็นสิ่งที่ทำให้ concurrent features เกิดขึ้นได้

จับสองอย่างนี้ไว้ แล้ว React จะเลิกทำให้คุณประหลาดใจ

<Callout title="การเปลี่ยนมุมมอง">
ถ้ามาจาก code สไตล์ jQuery คุณจะคิดเป็น **mutation**: "พอ user คลิก ก็ไปหา element แล้วเปลี่ยนมัน" React ขอให้คุณคิดเป็น **snapshot** แทน: "สำหรับ state นี้ UI หน้าตาแบบนี้" คุณไม่แตะ DOM เลย คุณแค่เปลี่ยน state แล้วอธิบาย UI ใหม่ การพลิกมุมนี้ — จาก *จะ update อย่างไร* ไปเป็น *มันควรเป็นอะไร* — คือหัวใจทั้งหมด
</Callout>
