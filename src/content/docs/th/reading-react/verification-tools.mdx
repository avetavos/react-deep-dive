## `tsc --noEmit` — ด่านแรกที่เร็ว แบบ strict

การ type-check อย่างเดียวจับแคตตาล็อกนี้ได้น้อยอย่างน่าตกใจโดยการออกแบบ — กฎส่วนใหญ่ของ React เอง (Rules of Hooks, effect cleanup, key identity, memoization) เป็น concern เรื่อง runtime/พฤติกรรมที่ type system ของ TypeScript ไม่มีทางเห็นได้ สิ่งที่ `tsc` *จับได้จริง* ภายใต้ config `strict`: การเรียก `useRef<T>()` แบบไม่มี argument (typing ของ React 19 ตัดครอบไม่มี argument ออกไป) และ return type ของ component ที่ annotate เป็น `JSX.Element`/`ReactElement` ในสาขาที่ต้อง return `null` ด้วย

```bash
npx tsc --noEmit
```

```text
BadUseRefNoArg.tsx(3,15): error TS2554: Expected 1 arguments, but got 0.
StatusIcon.tsx(3,44): error TS2322: Type 'null' is not assignable to type 'Element'.
```

ทั้งสองเป็น error จริง ปัจจุบัน ภายใต้ `@types/react@19` — ไม่ใช่แค่ style nitpick ดู **[AI Bug Catalog](/react/th/reading-react/ai-bug-catalog/)** entry 4 กับ 25

## `eslint-plugin-react-hooks@7.1.1` — diagnostic ของ compiler เอง มาเป็น lint error

เพราะ template `react-ts` ของ Vite ใช้ **oxlint** ไม่ใช่ ESLint กฎที่รู้จัก Hooks ต้อง install เองแบบชัดเจนพร้อม flat config:

```bash
npm install -D eslint @typescript-eslint/parser eslint-plugin-react-hooks
```

```js
// eslint.config.mjs
import reactHooks from 'eslint-plugin-react-hooks';
import tsParser from '@typescript-eslint/parser';
import { defineConfig } from 'eslint/config';

export default defineConfig([
  { files: ['**/*.{ts,tsx}'], languageOptions: { parser: tsParser } },
  reactHooks.configs.flat['recommended-latest'],
]);
```

`recommended-latest` เปิดทั้งกฎคลาสสิก rules-of-hooks/exhaustive-deps *และ* diagnostic ของ React Compiler เอง (`refs`, `set-state-in-render`, `immutability` และอื่น ๆ) ใน preset เดียว ห้าการละเมิดจริง รันผ่าน config นั้นเป๊ะ ๆ อันละกฎที่แคตตาล็อกของโมดูลนี้ต้องการ:

## `babel-plugin-react-compiler` — อ่าน bail-out จริง

compiler ระวังตัวโดยตั้งใจ: มันจะ memoize function เต็มรูปแบบ (call `_c()` memo-cache ห่อทุก sub-expression ที่ cache ได้) หรือปล่อยมันไว้เฉย ๆ ไม่แตะเลย โดย**ไม่มี build error ทั้งสองทาง** การ compile function `BadSetState` ตัวเดียวกับ example `set-state-in-render` ด้านบนด้วย `babel-plugin-react-compiler@1.0.0` ทำให้ function ถูกส่งผ่านไปแบบ byte-for-byte:

```text
import { jsxDEV as _jsxDEV } from "react/jsx-dev-runtime";
function BadSetState() {
  const [count, setCount] = useState(0);
  setCount(count + 1); // setState during render — Rules of React violation
  return /*#__PURE__*/_jsxDEV("p", {
    children: count
  }, void 0, false);
}
```

ไม่มี `_c()` ไม่มี memo cache — bail-out เงียบโดยการออกแบบ การ compile example การ mutate ของ `Themed` ก็ให้รูปแบบเดียวกัน: ส่งผ่านไปแบบไม่แตะ วิธีเดียวที่จะรู้ว่า component ถูกข้ามไปคือ diff compiled output กับตัวที่รู้ว่าดี หรือรัน ESLint rule ด้านบน ซึ่ง report การละเมิด*เดียวกัน*เป็น error จริง ตอน edit time โดยไม่ต้องอ่าน compiler output เลย ดู **[The React Compiler](/react/th/react-19/the-react-compiler/)** สำหรับคู่ input/output เต็ม ๆ พร้อม component ที่ compiler *memoize* จริง ๆ หน้าตาเป็นแบบไหน

## RTL + Vitest: smoke test จริง

component ที่ render แล้ว interact จริงยังคงเป็นหลักฐานตรงที่สุดที่คอร์สนี้มีสำหรับ "มันทำงานจริงไหม":

```tsx
// src/components/SmokeCounter.tsx
import { useState } from 'react';

export default function SmokeCounter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount((c) => c + 1)}>count: {count}</button>;
}
```

```tsx
// src/__tests__/smoke-counter.test.tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, test } from 'vitest';
import SmokeCounter from '../components/SmokeCounter';

test('a real RTL smoke test: click, then assert on what the user sees', async () => {
  const user = userEvent.setup();
  render(<SmokeCounter />);
  await user.click(screen.getByRole('button', { name: /count: 0/i }));
  expect(screen.getByRole('button', { name: /count: 1/i })).toBeInTheDocument();
});
```

## `<Profiler onRender>` — จำนวน commit จริง ไม่ใช่การเดา

`<Profiler id="..." onRender={...}>` เรียก callback ของมันหนึ่งครั้งต่อหนึ่ง commit ข้างใน พร้อม `phase` (`"mount"` หรือ `"update"`) และ timing data จริง — วิธีเชิงกลไกที่จะยืนยัน "component นี้ re-render จริงไหม" แทนที่จะเดาด้วยตา:

```tsx
// src/__tests__/profiler-counts.test.tsx
import { Profiler, useState } from 'react';
import { render, cleanup, act } from '@testing-library/react';
import { afterEach, expect, test } from 'vitest';

afterEach(cleanup);

function ProfiledChild({ label }: { label: string }) {
  return <span>{label}</span>;
}

function ProfiledParent() {
  const [tick, setTick] = useState(0);
  return (
    <div>
      <button onClick={() => setTick((t) => t + 1)}>{tick}</button>
      <ProfiledChild label="static" />
    </div>
  );
}

test('<Profiler onRender> records one commit per actual re-render, with real phase/duration data', () => {
  const commits: { phase: string }[] = [];
  const { getByRole } = render(
    <Profiler id="parent" onRender={(_id, phase) => commits.push({ phase })}>
      <ProfiledParent />
    </Profiler>,
  );

  expect(commits).toHaveLength(1);
  expect(commits[0].phase).toBe('mount');

  act(() => { getByRole('button').click(); });
  act(() => { getByRole('button').click(); });

  expect(commits).toHaveLength(3);
  expect(commits.slice(1).every((c) => c.phase === 'update')).toBe(true);
});
```

การ mount component ที่ห่อด้วย `<Profiler>` ให้ commit เป๊ะ ๆ หนึ่งครั้ง (`phase: 'mount'`); การ re-render ที่ขับด้วย state สองครั้งถัดมาให้อีกสองครั้ง (`phase: 'update'`) — รวมสาม commit พิสูจน์ด้วยการนับจำนวนครั้งที่ callback ถูกเรียกจริง ไม่ใช่การอนุมานจากพฤติกรรม นี่คือ primitive ตัวเดียวกับที่ Profiler tab ของ React DevTools เองสร้างขึ้นมาจาก ดู **[Rendering Performance](/react/th/performance-and-patterns/rendering-performance/)** สำหรับ `<Profiler>` ที่ใช้กับการ optimize จริง

## React DevTools: แท็บ Components กับ Profiler

extension ของ browser ให้สองแท็บที่เครื่องมือ command-line ของคอร์สนี้แทนไม่ได้:

- **Components** — ดู component tree ที่มีชีวิต, prop, state และค่าปัจจุบันของทุก hook ตามลำดับที่ hook ถูกเรียก; เลือก component เพื่อดูเป๊ะ ๆ ว่ามันได้รับอะไรและถืออะไรอยู่ โดยไม่ต้องเติม `console.log` สักบรรทัด
- **Profiler** — บันทึก session ของการ interact แล้วดู flame graph ของทุก commit: component ไหน render, ใช้เวลาเท่าไหร่ และ (สำคัญที่สุด) **ทำไม** แต่ละตัวถึง render — DevTools บอกชื่อ prop หรือ state ที่เปลี่ยนแล้วเป็นตัวกระตุ้น ซึ่งเป็นวิธีที่เร็วที่สุดในการยืนยันบั๊ก memoization ของ entry 19 หรือ 24 บนหน้าจริง แทนที่จะเป็น unit test
- **"Highlight updates when components render"** (setting ในแท็บ Profiler) — กระพริบกรอบรอบทุก component ที่ re-render สด ๆ ขณะคุณ interact กับหน้า เปิดตัวนี้บนหน้าที่สงสัยว่า over-render (Context กว้าง ๆ ที่ไม่ memoize; object แบบ inline ที่ทำลาย boundary ของ `memo`) ทำให้*ขอบเขต*ของปัญหามองเห็นได้ในไม่กี่วินาที ก่อนจะเขียน test สักตัว

## `<StrictMode>` ตอน development

`<StrictMode>` ตั้งใจ double-render component และ double-invoke setup→cleanup→setup ของ effect ตอน development — พิสูจน์แล้ว ไม่ใช่แค่บรรยาย ใน **[Rendering & Reconciliation](/react/th/foundations/rendering-and-reconciliation/)**:

```text
✓ StrictMode (dev) renders twice and runs setup -> cleanup -> setup once on mount
✓ without StrictMode, the same component renders and effects run exactly once
```

การเปิดมันทิ้งไว้ไม่มีต้นทุนใด ๆ ใน production (มันไม่ทำอะไรเลยที่นั่น) และเผยพฤติกรรมแบบ impure ที่แคตตาล็อกของโมดูลนี้เต็มไปด้วย — mutation ตอน render, effect ที่ cleanup ไม่ undo setup ของมันเต็มที่ — เป็นอาการตอน *development* ก่อนที่มันจะถูก ship ทั้งคู่ ดู **[Production & Ecosystem](/react/th/tooling-and-production/production-and-ecosystem/)** สำหรับความต่างของ dev/production build ที่เรื่องนี้ยึดถือ

## `prerender` ของ `react-dom/static` — ดู HTML ที่แน่ชัดที่ first paint ของ user จะโชว์

`prerender` ของ `react-dom/static` (และ `prerenderToNodeStream`) รอข้อมูลทั้งหมดจนจบก่อนจะ return — ไม่เหมือน `renderToString`/`renderToPipeableStream` มันไม่เคยปล่อย shell ที่ยังไม่สมบูรณ์ออกมา สิ่งที่ได้กลับมาเลยเป็น HTML ที่*แน่ชัด*สมบูรณ์ที่ first paint จริงจะโชว์:

```tsx
// src/components/StaticPage.tsx
function StaticPage() {
  return (
    <html>
      <body>
        <p data-testid="marker">static</p>
      </body>
    </html>
  );
}

export default StaticPage;
```

```tsx
// src/__tests__/static-prerender.test.tsx
import { prerender } from 'react-dom/static';
import { expect, test } from 'vitest';
import StaticPage from '../components/StaticPage';

test('react-dom/static prerender() resolves a real, complete HTML stream (Node runtime)', async () => {
  const { prelude } = await prerender(<StaticPage />);
  const reader = prelude.getReader();
  const decoder = new TextDecoder();
  let html = '';
  for (;;) {
    const { done, value } = await reader.read();
    if (done) break;
    html += decoder.decode(value);
  }
  expect(html).toContain('<p data-testid="marker">static</p>');
});
```

คุณค่าของมันสำหรับบั๊ก hydration โดยเฉพาะ: การส่อง HTML ที่แน่ชัด สมบูรณ์ รอครบแล้วนี้ตอน build time — ก่อน client JavaScript ไหนจะรันเลย — คือสิ่งที่ทำให้จับค่าที่จะไม่ตรงกันทันทีที่ client รัน component เดียวกันซ้ำได้ pattern `Date.now()`/`Math.random()` ของ entry 22 เป็นตัวอย่างที่ชัดที่สุด `prerender` รันการรันซ้ำฝั่ง client เองไม่ได้ (ต้องใช้ browser จริงหรือ `hydrateRoot` พิสูจน์แยกไว้ใน entry 22 ของ **[AI Bug Catalog](/react/th/reading-react/ai-bug-catalog/)**) — แต่การอ่าน output ของมันคือที่ที่ถูกที่สุดในการสังเกตค่าที่ไม่ควรจะเสถียรตั้งแต่แรก

## harness ของคอร์สนี้เอง: compile ทุก snippet

ทุก code fence ในคอร์สนี้ที่มี comment บรรทัดแรกเปล่า ๆ แบบ `// path.ext` คือไฟล์จริง ถูกเก็บโดย `tools/verify-snippets.mjs` เข้า directory ที่ namespace ไว้ต่อบท แล้ว type-check ใน `tsc --noEmit` รอบเดียวข้ามทั้งคอร์ส:

```bash
node tools/verify-snippets.mjs
```

```text
no type errors.

Per-module fence summary (collected / skipped-no-path / expect-error / tests):
  reading-react: ... (see this module's own gate run)
  ...
```

fence ที่ตั้งใจโชว์โค้ดที่พังหรือมีพฤติกรรมผิด (เหมือน example "โค้ดที่ AI มักเขียน" ส่วนใหญ่ใน **[AI Bug Catalog](/react/th/reading-react/ai-bug-catalog/)**) ขึ้นต้นด้วย `// @expect-error <เหตุผล>` เพื่อให้ harness ข้ามการเก็บมัน — เนื้อหาบทเรียนพก output จริงของ `tsc`/`eslint`/console ที่จับแยกไว้แล้วแทนที่จะให้ harness พยายาม reproduce ความล้มเหลวที่ตั้งใจไว้ทุกรอบ
