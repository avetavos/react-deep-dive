## ไล่รีวิวทีละบั๊ก

### Hooks กับ dependency: `useRef()` ที่ไม่มีค่าเริ่มต้น

`AvatarUpload` เรียก `useRef<HTMLInputElement>()` โดยไม่มี argument เลย

<SpotTheBug code={`function AvatarUpload() {
  const inputRef = useRef<HTMLInputElement>();
  return (
    <div>
      <button onClick={() => inputRef.current?.click()}>Choose avatar</button>
      <input ref={inputRef} type="file" style={{ display: 'none' }} />
    </div>
  );
}`}>
`@types/react@19` ประกาศ `useRef` overload ไว้สามแบบพอดี และไม่มีแบบไหนเลยที่รับศูนย์ argument — นิสัยเก่า "ไม่ใส่ argument แล้วได้ `undefined` โดยปริยาย" จาก type definition รุ่นก่อนหน้าไม่ตรงกับ overload ไหนเลยอีกต่อไป นี่คือ type error จริง ปัจจุบัน ที่ตรวจสอบแล้วกับ React/TypeScript เวอร์ชันนี้เป๊ะ ๆ:

```text
error TS2554: Expected 1 arguments, but got 0.
```

`tsc --noEmit` จับตัวนี้ได้ก่อนที่แอปจะถูก ship เลยด้วยซ้ำ — เป็นบั๊กเดียวในรีวิวนี้ที่แค่ type-check เฉย ๆ ก็เจอ
</SpotTheBug>

### ขอบเขต server/client: `useSyncExternalStore` ที่ไม่มี `getServerSnapshot`

`ThemeToggle` เรียก `useSyncExternalStore(subscribe, getSnapshot)` — สอง argument ไม่มีตัวที่สาม

<SpotTheBug code={`export function ThemeToggle() {
  const current = useSyncExternalStore(subscribe, getSnapshot);
  return <button onClick={() => setTheme(current === 'light' ? 'dark' : 'light')}>Theme: {current}</button>;
}`}>
argument ตัวที่สาม `getServerSnapshot` จะสำคัญก็ต่อเมื่อโค้ดนี้ render บนเซิร์ฟเวอร์ — แต่การไม่ใส่มันไม่ได้แค่ fallback ไปเป็นอะไรที่สมเหตุสมผลเงียบ ๆ react.dev บอกไว้ตรง ๆ ว่า "ถ้าไม่ใส่ argument นี้ การ render component บนเซิร์ฟเวอร์จะ throw error" พิสูจน์ใน probe ด้วย `renderToString`:

```text
Missing getServerSnapshot, which is required for server-rendered content. Will revert to client rendering.
```

เหตุผลที่มันต้อง throw แทนที่จะเสื่อมคุณภาพลงเงียบ ๆ คือเรื่อง hydration: เซิร์ฟเวอร์ไม่มี `window` ให้เรียก `getSnapshot` ฝั่ง client ได้ และ render แรกของ client ต้องตรงกับ markup ของเซิร์ฟเวอร์เป๊ะ ไม่งั้น React จะ log ว่าไม่ตรงกัน วิธีแก้คือใส่ argument ตัวที่สาม `getServerSnapshot` ที่คืนค่าคงที่ที่ใช้ได้กับ render แรก (บนเซิร์ฟเวอร์)
</SpotTheBug>

### ความเป็นเจ้าของ state: setter ของ `useOptimistic` ถูกเรียกนอก Transition

`handleToggle` ของ `MarketingOptIn` เรียก `setOptimisticOptIn` ตรง ๆ ใน event handler ธรรมดา แล้วต่อด้วย `.then()` — ไม่มี `startTransition` ที่ไหนเลย

<SpotTheBug code={`function handleToggle() {
  setOptimisticOptIn(!optimisticOptIn);
  saveMarketingOptIn(!optimisticOptIn).then(() => setOptIn(!optIn));
}`}>
ตาม react.dev: *"ต้องเรียก optimistic setter function ภายใน `startTransition` หรือภายใน Action เท่านั้น การเรียก setter นอก Action จะทำให้ optimistic state revert กลับทันที เพราะไม่มี Transition คอยยึดมันไว้"* พิสูจน์ใน probe ด้วย console message จริง:

```text
An optimistic state update occurred outside a transition or action. To fix, move the update to an action, or wrap with startTransition.
```

ปุ่มจะแสดง "Subscribed" แวบหนึ่งแล้วก็ revert กลับ — เพราะไม่มี Transition ให้ React ยึด optimistic value ไว้จนกว่า state จริงจะนิ่ง วิธีแก้คือห่อลำดับทั้งหมดด้วย `startTransition(async () => {...})`
</SpotTheBug>

### React 19 Actions: `useFormState` แทนที่จะเป็น `useActionState`

`NameForm` import `useFormState` จาก `react-dom`

<SpotTheBug code={`import { useFormState } from 'react-dom';

function NameForm() {
  const [state, formAction] = useFormState(updateNameAction, {});
  return (
    <form action={formAction}>
      <input name="name" />
      <button type="submit">Save</button>
      {state.error && <p role="alert">{state.error}</p>}
    </form>
  );
}`}>
`useFormState` ยังมีอยู่ใน `react-dom@19.2.8` — ไม่ใช่ API ที่ถูกลบออกไป — แต่เป็นชื่อเก่าก่อนเปลี่ยนชื่อ และการเรียกมันพิมพ์คำเตือน deprecation จริงที่จับได้จาก React เวอร์ชันนี้เป๊ะ ๆ:

```text
ReactDOM.useFormState has been renamed to React.useActionState. Please update NameFormBad to use React.useActionState.
```

นอกจากคำเตือนแล้ว component นี้ยังไม่มีทางแสดง pending UI ได้เลย — tuple ที่ `useFormState` คืนมาไม่มี element ตัวที่สาม `isPending` แบบที่ `useActionState` มี วิธีแก้คือ import `useActionState` จาก `react` แทน ซึ่งคืนรูปร่างเดียวกันบวก `isPending`
</SpotTheBug>

### React 19 Actions: `useFormStatus` อยู่ใน component เดียวกับ `<form>`

`NotificationsForm` เรียก `useFormStatus()` ตรง ๆ ใน function component เดียวกับที่ render `<form>`

<SpotTheBug code={`function NotificationsForm() {
  const [state, formAction] = useActionState(updateNotificationsAction, {});
  const { pending } = useFormStatus();
  return (
    <form action={formAction}>
      <button type="submit" disabled={pending}>{pending ? 'Saving…' : 'Save'}</button>
    </form>
  );
}`}>
`useFormStatus` รายงานสถานะ pending ของ `<form>` ที่เป็น**บรรพบุรุษ**ที่ใกล้ที่สุด — และ component ที่ render `<form>` ไม่ใช่ descendant ของตัวเอง โค้ดนี้คอมไพล์และรันได้โดยไม่มี error หรือ warning เลย — มันแค่ไม่ทำงานเลยตลอด พิสูจน์ใน probe แล้ว: กด submit บน action ที่ใช้เวลา 20ms แล้วเช็คปุ่มอีก 5ms ต่อมา `pending` ไม่เคยกลายเป็น `true` เลย ทั้งที่ action ยังทำงานอยู่จริง

วิธีแก้คือย้าย `useFormStatus` ไปไว้ใน child component แยกต่างหากที่ render อยู่*ภายใน* `<form>` — เหมือนที่บทเรียน Server Components ของคอร์สนี้เคยแสดงไว้กับ hook ตัวเดียวกันนี้
</SpotTheBug>

### Effect เทียบกับ event: `Date.now()` ถูกอ่านระหว่าง render

`LastSaved` อ่าน `Date.now()` ตรง ๆ ใน render body

<SpotTheBug code={`function LastSaved() {
  return <p>Last saved: {Date.now()}</p>;
}`}>
`Date.now()` ตามนิยามแล้วให้ค่าต่างกันทุกครั้งที่ถูกเรียก component ที่ render ครั้งเดียวบนเซิร์ฟเวอร์จะได้ HTML ค่าหนึ่ง พอ component ตัวเดียวกันนั้นรัน*อีกครั้ง*บน client เพื่อ hydrate มันเรียก `Date.now()` เป็นครั้งที่สองแล้วได้ค่าที่ต่างออกไป — hydration mismatch แบบตำราเป๊ะ ๆ พิสูจน์ใน probe แล้ว (เซิร์ฟเวอร์ render ด้วย timestamp ที่ mock ไว้ค่าหนึ่ง client hydrate ด้วยอีกค่าหนึ่งห่างกันห้าวินาที):

```text
Hydration failed because the server rendered text didn't match the client. As a result this
tree will be regenerated on the client. This can happen if a SSR-ed Client Component used:

- A server/client branch `if (typeof window !== 'undefined')`.
- Variable input such as `Date.now()` or `Math.random()` which changes each time it's called.
- Date formatting in a user's locale which doesn't match the server.
- External changing data without sending a snapshot of it along with the HTML.
- Invalid HTML tag nesting.

It can also happen if the client has a browser extension installed which messes with the
HTML before React loaded.

https://react.dev/link/hydration-mismatch

  <LastSaved>
    <p>
+     1700000005000
-     1700000000000
```

ข้อความ error ของ React เองระบุ `Date.now()` เป็นสาเหตุที่รู้จักไว้ตรง ๆ เลย วิธีแก้คือคำนวณ timestamp เฉพาะฝั่ง client เท่านั้น ในตัว effect เพื่อให้ทั้ง render ของเซิร์ฟเวอร์และ render แรกของ client เห็นตรงกันด้วย placeholder เดียวกัน
</SpotTheBug>

// src/settings/MarketingOptIn.tsx
import { startTransition, useOptimistic, useState } from 'react';

// A tiny simulated backend call — real, so a test can actually await it.
export async function saveMarketingOptIn(_v: boolean): Promise<void> {}

// FIX (useOptimistic outside an Action): the setter is wrapped in
// startTransition, so React has a Transition to "hold" the optimistic value
// in until the real state settles — otherwise it reverts immediately.
export function MarketingOptIn({ initial }: { initial: boolean }) {
  const [optIn, setOptIn] = useState(initial);
  const [optimisticOptIn, setOptimisticOptIn] = useOptimistic(optIn);

  function handleToggle() {
    startTransition(async () => {
      setOptimisticOptIn(!optimisticOptIn);
      await saveMarketingOptIn(!optimisticOptIn);
      setOptIn(!optIn);
    });
  }

  return <button onClick={handleToggle}>{optimisticOptIn ? 'Subscribed' : 'Subscribe'}</button>;
}

export function setTheme(next: Theme) {
  theme = next;
  listeners.forEach((l) => l());
}

function subscribe(listener: () => void) {
  listeners.add(listener);
  return () => listeners.delete(listener);
}

function getSnapshot(): Theme {
  return theme;
}

// FIX (missing getServerSnapshot): required the moment this store can render
// on the server — omitting it throws, specifically to protect the first
// hydration pass from disagreeing with the client.
function getServerSnapshot(): Theme {
  return 'light';
}

export function ThemeToggle() {
  const current = useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);
  return <button onClick={() => setTheme(current === 'light' ? 'dark' : 'light')}>Theme: {current}</button>;
}

// FIX (Date.now() in render -> hydration mismatch): the timestamp is read
// only on the client, inside an effect, after hydration has already
// reconciled — never during the render that both server and client run.
export function LastSaved() {
  const [time, setTime] = useState<number | null>(null);
  useEffect(() => {
    setTime(Date.now());
  }, []);
  return <p>{time === null ? 'Last saved: —' : `Last saved: ${time}`}</p>;
}

## สิ่งที่เปลี่ยนและเหตุผล

| # | บั๊ก | หมวด | วิธีแก้ |
|---|---|---|---|
| 1 | `useRef<HTMLInputElement>()` — ไม่มี argument | Hooks & deps | `useRef<HTMLInputElement>(null)` — React 19 types บังคับต้องใส่ |
| 2 | `useSyncExternalStore(subscribe, getSnapshot)` — ไม่มี `getServerSnapshot` | Server/client boundary | เพิ่ม argument ตัวที่สาม `getServerSnapshot` |
| 3 | `setOptimisticOptIn(...)` ถูกเรียกตรง ๆ ใน event handler | State ownership | ห่อลำดับทั้งหมดด้วย `startTransition(async () => {...})` |
| 4 | `useFormState` (จาก `react-dom`) — API ชื่อเก่าก่อนเปลี่ยน | React 19 Actions | `useActionState` (จาก `react`) — รูปร่างเดียวกันบวก `isPending` |
| 5 | `useFormStatus()` อยู่ใน component เดียวกับที่ render `<form>` | React 19 Actions | ย้ายไปไว้ใน child `SubmitButton` ที่ render ในฟอร์ม |
| 6 | `Date.now()` ถูกอ่านตรง ๆ ใน render ของ `LastSaved` | Effects vs events | คำนวณใน effect — เฉพาะฝั่ง client หลัง hydration |

## Mental Model

สามในหกบั๊กนี้ (`useRef()`, `getServerSnapshot`, `Date.now()`/hydration) เป็นข้อเท็จจริงที่เครื่องมือตรวจให้คุณได้เลย — type error จริง, exception ที่ throw จริง, ข้อความ mismatch ที่จับได้จริง — ทันทีที่คุณรัน check ที่ถูกต้อง (`tsc`, server render, hydration test) อีกสามบั๊กที่เหลือ (`useOptimistic` นอก Transition, `useFormState` ที่ขาด `isPending`, `useFormStatus` ผิดที่) เป็นข้อเท็จจริงเรื่องรูปร่างของ API — ทุกตัวคอมไพล์และรันได้โดยไม่พัง วิธีเดียวที่จะจับได้คือรู้ว่า react.dev รับประกันอะไรไว้ในปัจจุบัน แล้วเช็คว่าโค้ดยังรักษาคำรับประกันนั้นอยู่จริงหรือเปล่า

## ความเข้าใจผิดที่พบบ่อย

- **"ถ้าไม่ throw หรือ warning แปลว่าใช้ React 19 API ถูกต้องแล้ว"** `useFormState` พิมพ์คำเตือน deprecation จริง `useOptimistic` นอก Transition ก็พิมพ์คำเตือนจริงเหมือนกัน — แต่ `useFormStatus` ที่อยู่ผิด component ไม่ให้อะไรเลยแม้แต่คำใบ้ มันแค่ไม่ทำงานตลอดไปเงียบ ๆ
- **"argument ตัวที่สามของ `useSyncExternalStore` เป็นแค่ของแถมที่ไม่บังคับ เหมือน default parameter"** มันบังคับทันทีที่โค้ดนี้ render บนเซิร์ฟเวอร์ได้ — พิสูจน์ไปแล้วด้านบนว่ามัน throw แทนที่จะเสื่อมคุณภาพลงเงียบ ๆ เพื่อปกป้อง hydration โดยเฉพาะ
- **"ไลบรารี optimistic UI จัดการเรื่องข้อกำหนด Transition ให้เราแล้ว"** `useOptimistic` คือ primitive ของมันเอง — ไม่มีอะไรห่อ Transition ให้อัตโนมัติ โค้ดที่เรียกใช้ต้องทำเองเสมอ
