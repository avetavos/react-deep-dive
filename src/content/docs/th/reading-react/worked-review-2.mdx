## ฟีเจอร์นี้คืออะไร

โจทย์ที่ให้ AI คือ *"เพิ่มแดชบอร์ดโปรเจกต์: กล่องค้นหาที่ใช้ `use()`, แผงแสดงเมตริกแบบสดที่รีเฟรชเมื่อโปรเจกต์ที่เลือกเปลี่ยน, แผงรายละเอียดต่อโปรเจกต์ที่มีช่องโน้ตกับ list รายการที่เกี่ยวข้อง และปุ่มรีเฟรชที่ห่อด้วย error boundary"* ผลลัพธ์ด้านล่างคอมไพล์ผ่าน, `tsc --noEmit` ผ่านทุกไฟล์ และทุกส่วนก็ใช้แพทเทิร์นของ concurrent React ที่โมดูล Concurrent & Suspense ของคอร์สนี้สอนไปแล้ว อ่านตาม[ลำดับการอ่าน](/react/th/reading-react/)ของโมดูลนี้ที่ปรับให้เข้ากับฟีเจอร์แบบ concurrent: hooks กับ dependency, effect เทียบกับ event, และสมมติฐานเรื่อง memo/compiler ล้วนโผล่มาที่นี่ — แค่สวมคราบ `startTransition`, `use()` และ `useDeferredValue` แทน `useEffect` ธรรมดา โค้ดนี้มี **บั๊กจริง 6 จุด** ซึ่งไม่มีจุดไหนเลยที่ `tsc --noEmit` จับได้

## ไล่รีวิวทีละบั๊ก

### Hooks กับ dependency: `use()` ถูกเรียกด้วย promise ที่สร้างใหม่ทุกครั้งใน render

`SearchResultsList` เรียก `fetchResults(query)` ตรง ๆ ใน render body เลย

<SpotTheBug code={`function SearchResultsList({ query }) {
  const results = use(fetchResults(query)); // a NEW promise every render
  return <ul>{results.map((r) => <li key={r.id}>{r.title}</li>)}</ul>;
}`}>
`use()` ไม่ได้ fetch หรือ cache อะไรเลย — มันแค่อ่าน promise ที่คุณส่งให้เท่านั้น การเรียก `fetchResults(query)` ตรง ๆ ใน render สร้าง promise ใหม่ทุก render จริง ๆ ทำให้ component suspend ค้างไม่มีที่สิ้นสุดหรือ refetch ทุก render ขึ้นอยู่กับจังหวะเวลา พิสูจน์ใน probe แล้ว: เรียก fetch ที่ไม่มี cache สองครั้งด้วย query เดียวกัน ได้ promise แยกกัน**สองตัว** (เรียกจริงสองครั้ง) ในขณะที่เวอร์ชันที่มี cache คืน reference ของ promise ตัวเดียวกันทั้งสองครั้ง

```text
✓ as generated: calling the fetch directly in render builds a NEW promise every single call
✓ fixed: getResultsPromise caches by query — the SAME promise reference comes back

Test Files  1 passed (1)
     Tests  2 passed (2)
```

วิธีแก้คือ cache promise ตาม query ไว้ใน `Map` เพื่อให้ render ซ้ำ ๆ (และการเรียก query เดิมซ้ำ ๆ) อ่าน promise ตัวเดียวกันที่กำลัง in-flight อยู่แล้ว
</SpotTheBug>

### Effect เทียบกับ event: `startTransition(async)` เสียลำดับความสำคัญหลัง `await`

`handleChange` ห่อทุกอย่างด้วย `startTransition(async () => {...})` แล้วเรียก `setLastLogged(next)` หลัง `await logSearchAnalytics(next)`

<SpotTheBug code={`function handleChange(next) {
  startTransition(async () => {
    setQuery(next); // before the first await — covered
    await logSearchAnalytics(next);
    setLastLogged(next); // after the await — NOT re-wrapped
  });
}`}>
ส่วน troubleshooting ของ `useTransition` ใน react.dev บอกไว้ชัดเจนว่า มีแค่โค้ดที่อยู่**ก่อน** `await` ตัวแรกเท่านั้นที่นับเป็นส่วนหนึ่งของ transition โดยอัตโนมัติ `setLastLogged(next)` รันหลัง await และไม่ถูกห่อด้วย `startTransition` ของตัวเอง — มันเลยกลายเป็น update แบบเร่งด่วนธรรมดาไปเงียบ ๆ พิสูจน์ด้วยกลไกเดียวกับที่ update ที่ทำให้ suspend จะเจอจริง: `setState` ที่ทำให้ `Suspense` boundary suspend รันแบบเดียวกันทั้งแบบห่อใหม่และไม่ห่อใหม่ ถ้าไม่ห่อใหม่ boundary จะ fallback ไปหน้า loading ทันที ถ้าห่อใหม่ React จะคงเนื้อหาเดิมไว้บนจอระหว่างที่เนื้อหาใหม่โหลดอยู่เบื้องหลัง — ตรงตามสัญญาที่ `isPending` บอกไว้แต่บั๊กนี้แอบทำลายไปเงียบ ๆ

```text
✓ as generated: a setQuery after a bare await is NOT part of the transition — Suspense falls back immediately
✓ fixed: re-wrapping setQuery after await keeps it part of the transition — old content stays, no fallback

Test Files  1 passed (1)
     Tests  2 passed (2)
```

วิธีแก้คือห่อ `startTransition(() => setLastLogged(next))` รอบ ๆ การเรียกหลัง `await` อีกชั้นหนึ่ง
</SpotTheBug>

### Effect เทียบกับ event: effect fetch ที่ไม่มีการ abort/จัดการ race

`LiveMetrics` fetch เมตริกตาม `projectId` ใน `useEffect` โดยไม่มีการยกเลิกใด ๆ เลย

<SpotTheBug code={`function LiveMetrics({ projectId }) {
  const [value, setValue] = useState(null);
  useEffect(() => {
    fetchMetric(projectId).then((result) => setValue(result));
  }, [projectId]);
  return <output>{value === null ? 'loading…' : value}</output>;
}`}>
ถ้า `projectId` เปลี่ยนเร็ว (คลิกสลับโปรเจกต์ไปมา) request ที่เก่ากว่าและช้ากว่าอาจ resolve **หลัง** request ที่ใหม่กว่าและเร็วกว่า แล้วเขียนทับ state ที่สดใหม่ด้วยข้อมูลเก่า พิสูจน์ใน probe ด้วยคู่ request ที่ตั้งใจให้ช้าแล้วเร็ว (ตัวช้าเริ่มก่อนแต่จะ resolve ทีหลัง): สลับจากโปรเจกต์ที่ช้าไปโปรเจกต์ที่เร็ว ทำให้แผงยังแสดงค่าของโปรเจกต์ที่**ช้าและเก่าแล้ว**อยู่

```text
✓ as generated: a slow, stale response overwrites a newer, faster one
✓ fixed: LiveMetrics aborts the previous request, so the fast response always wins

Test Files  1 passed (1)
     Tests  2 passed (2)
```

วิธีแก้คือ `AbortController` ที่สร้างในตัว effect แล้วยกเลิกใน cleanup — request เดิมของ `projectId` ก่อนหน้าจะถูกยกเลิกทันทีที่ `projectId` เปลี่ยนอีกครั้ง
</SpotTheBug>

### สมมติฐานเรื่อง memo/compiler: `useDeferredValue` ที่ไม่มี `initialValue`

`ItemDetail` defer `item.related` ด้วย `useDeferredValue(item.related)` — ไม่มี argument ที่สอง

<SpotTheBug code={`const deferredRelated = useDeferredValue(item.related);`}>
ตั้งแต่ React 19 `useDeferredValue` รับ `initialValue` แบบไม่บังคับ ซึ่งใช้แค่ตอน render แรกของ component เท่านั้น react.dev บอกไว้ชัดเจนว่า **ถ้าไม่มี** ตัวนี้ "hook จะไม่ defer ระหว่าง render แรกเลย" — render แรกจะได้ค่าจริงตรง ๆ ไม่มีค่า placeholder ที่ถูก defer เลย พิสูจน์ใน probe แล้ว: render โดยไม่มี `initialValue` แสดง list รายการที่เกี่ยวข้องแบบเต็ม ๆ จริง ๆ ตั้งแต่ render แรกเลย (ไม่มีการ defer เกิดขึ้น); render `useDeferredValue(related, [])` แสดง placeholder ว่างเปล่าใน render แรกเดียวกันนั้นแทน

```text
✓ as generated: useDeferredValue(related) with no initialValue shows the REAL list on the first render
✓ fixed: ItemDetail(useDeferredValue(related, [])) shows the empty placeholder on the first render

Test Files  1 passed (1)
     Tests  2 passed (2)
```

วิธีแก้คือ `useDeferredValue(item.related, [])` — placeholder ที่ถูกกำหนดไว้ชัดเจนและถูกสำหรับ render แรก ทันทีหลังจากที่ remount จาก key-reset ด้านล่างทำให้ component นี้เป็น instance ใหม่
</SpotTheBug>

### Key กับ identity: ไม่มี key บน per-item subtree — โน้ตร่างหลุดข้ามรายการ

`Dashboard` render `<ItemDetail item={selected} />` โดยไม่มี `key` เลย — การสลับ `selectedId` จึง re-render `ItemDetail` instance*ตัวเดิม*ในที่เดิม

<SpotTheBug code={`<ItemDetail item={selected} />`}>
`ItemDetail` มี state ของตัวเอง (`notes`) ซึ่งไม่เกี่ยวอะไรกับ `item.title`/`item.related` เลย — React ไม่มีทางรู้ว่าควร reset มันหรือเปล่า ถ้าไม่มี `key` การสลับจากรายการหนึ่งไปอีกรายการก็แค่อัปเดต prop บน component instance*ตัวเดิม*เท่านั้น `notes` — ซึ่งเป็น state ที่ React ไม่มีเหตุผลจะไปแตะ — เลยแค่ตกทอดต่อไปเฉย ๆ พิสูจน์ใน probe แล้ว: พิมพ์โน้ตร่างตอนดูรายการ A สลับไปรายการ B แล้ว textarea ยังมีข้อความร่างตัวเดิมอยู่ ตอนนี้ผูกอยู่กับรายการที่ผิดไปแล้ว

### Effect เทียบกับ event: error boundary ไม่จับ throw ที่เกิดใน event handler

ปุ่มของ `DangerZone` เรียก `refreshDashboardData` ตรง ๆ เป็น `onClick` โดยพึ่งพา `ErrorBoundary` ที่ห่ออยู่ใน `Dashboard`

<SpotTheBug code={`export function DangerZone() {
  return <button onClick={refreshDashboardData}>Refresh data</button>;
}`}>
error boundary จับ error ที่ throw ระหว่าง**การ render** (และใน lifecycle method) ของ component ที่อยู่ใต้มันเท่านั้น — ไม่เคยจับใน event handler เลย เพราะ event handler เป็นแค่ callback ของ JS ธรรมดาที่รันนอก render ของ React พิสูจน์ใน probe แล้ว: คลิกปุ่มที่ throw ตรง ๆ ใน `onClick` ซึ่งห่อด้วย error boundary จริง ไม่เคยแสดง fallback ของ boundary เลย — exception หลุดไปถึง global `error` event ของ browser เอง (`message: "handler-boom"`) ข้าม `getDerivedStateFromError` ไปเลย

```text
✓ as generated: a throw inside an onClick handler is NOT caught by the error boundary
✓ fixed: DangerZone catches the same throw itself with try/catch and shows a local error

Test Files  1 passed (1)

```

วิธีแก้คือจัดการ throw ตรงที่มันเกิดขึ้นจริง ๆ: `try/catch` ธรรมดาในตัว event handler เอง พร้อม local error state — error boundary ไม่มีทางเห็นมันอยู่แล้ว

    setTimeout(() => resolve([{ id: `${query}-1`, title: `Result for "${query}"` }]), 5);
  });

  return Promise.resolve(void query);
}

const cache = new Map<string, Promise<SearchResult[]>>();

// FIX (use() reading a stable promise): cached per query, never a fresh
// promise on every render — use() only reads a promise, it never caches one.
export function getResultsPromise(query: string): Promise<SearchResult[]> {
  if (!query) return Promise.resolve([]);
  if (!cache.has(query)) cache.set(query, fetchResults(query));
  return cache.get(query)!;
}

// src/dashboard/LiveMetrics.tsx
import { useEffect, useState } from 'react';

// A tiny simulated backend, deliberately slower for one id, so a real
// out-of-order response race can be reproduced deterministically in a test.
export function fetchMetric(projectId: string, signal: AbortSignal): Promise<number> {
  const delayMs = projectId === 'slow' ? 30 : 5;
  return new Promise((resolve, reject) => {
    const id = setTimeout(() => resolve(projectId === 'slow' ? 111 : 222), delayMs);
    signal.addEventListener('abort', () => {
      clearTimeout(id);
      reject(new DOMException('aborted', 'AbortError'));
    });
  });
}

// FIX (effect fetch race): an AbortController cancels the in-flight request
// for the PREVIOUS projectId, so a slow, stale response can never overwrite
// a newer, faster one.
export function LiveMetrics({ projectId }: { projectId: string }) {
  const [value, setValue] = useState<number | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    setValue(null);
    fetchMetric(projectId, controller.signal)
      .then((result) => setValue(result))
      .catch((err: Error) => {
        if (err.name !== 'AbortError') throw err;
      });
    return () => controller.abort();
  }, [projectId]);

  return <output data-testid="metric">{value === null ? 'loading…' : value}</output>;
}

import { Component, type ReactNode } from 'react';

type State = { error: Error | null };

export class ErrorBoundary extends Component<{ children: ReactNode; fallback: ReactNode }, State> {
  state: State = { error: null };

  static getDerivedStateFromError(error: Error): State {
    return { error };
  }

  render() {
    if (this.state.error) return this.props.fallback;
    return this.props.children;
  }
}

## Mental Model

ฟีเจอร์ concurrent ของ React (`startTransition`, `use()`, `useDeferredValue`) ยังคงสร้างอยู่บน primitive เดียวกับที่โมดูล Hooks ของคอร์สนี้สอนไปแล้ว — dependency array, การเปรียบเทียบ reference, state ของ component instance ของตัวเอง — มันแค่เอา primitive เหล่านั้นไปใช้กับ*เมื่อไร*และ*ลำดับไหน*ที่งานจะเกิดขึ้น ไม่ใช่แค่*อะไร*ที่จะถูก render บั๊กทุกจุดในรีวิวนี้คือรูปแบบความล้มเหลวที่คุ้นเคยแบบเดียวกัน (ค่าที่ค้าง, reference ที่เปลี่ยนทั้งที่ไม่ควรเปลี่ยน, state ที่ควร reset) แค่สวมคราบของ concurrent API เท่านั้นเอง

## ความเข้าใจผิดที่พบบ่อย

- **"`startTransition(async () => {...})` ทำให้ callback ทั้งก้อนกลายเป็น low-priority"** มีแค่โค้ดก่อน `await` ตัวแรกเท่านั้นที่นับเป็นส่วนหนึ่งของ transition โดยอัตโนมัติ — พิสูจน์ไปแล้วสองครั้งด้านบน (ทั้งห่อใหม่และไม่ห่อใหม่) กับ Suspense boundary จริง
- **"error boundary ที่ห่อ component ป้องกันทุกอย่างที่ component นั้นทำ"** มันป้องกันแค่ error ตอน render ของ subtree นั้น — ไม่ใช่ click handler ไม่ใช่ promise ที่ reject นอก `use()` และไม่ใช่โค้ดของตัว boundary เอง
- **"ถ้า prop ของ component ไม่เปลี่ยน state ภายในของมันก็ปลอดภัย"** state `notes` ของ `ItemDetail` ไม่เกี่ยวอะไรกับ `item.related`/`item.title` เลย — parent ต้อง opt-in การ reset ด้วย `key` เอง ไม่งั้น state ที่ควรเป็นของแต่ละรายการก็จะตกทอดต่อไปเงียบ ๆ
