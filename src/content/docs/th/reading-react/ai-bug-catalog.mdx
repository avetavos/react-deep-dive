## Hooks กับ dependency ของมัน

### 1. Effect ที่ขาด cleanup

```tsx
// src/components/ChatRoomNoCleanup.tsx — as generated
import { useEffect } from 'react';

function ChatRoomNoCleanup({ roomId }: { roomId: string }) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect();
    // No return statement — nothing ever tears this connection down.
  }, [roomId]);
  return null;
}
```

`useEffect` มีไว้ sync กับ external system และทุกการ sync ต้องการวิธี undo ถ้าไม่มี cleanup function React ไม่มีอะไรให้เรียกเมื่อ `roomId` เปลี่ยนหรือ component unmount — connection เก่าก็แค่รันต่อไปเงียบ ๆ อยู่ข้าง ๆ ไม่ว่า effect รอบถัดไปจะตั้งค่าอะไรไว้

**อาการ — จำนวน connection ที่วัดได้จริง** (counter ที่แชร์กันข้าม instance ของ `createConnection` ทุกตัว พิสูจน์แล้วใน probe):

```text
✓ an effect with no cleanup leaves a real connection open after the component unmounts
✓ remounting the same room without cleanup accumulates connections instead of replacing one

Test Files  1 passed (1)
     Tests  2 passed (2)
```

การ unmount component ทิ้งจำนวน connection ไว้ที่ `1` ไม่ใช่ `0`; การสลับห้องทิ้งไว้ที่ `2` (ทั้ง "general" กับ "random" เปิดพร้อมกัน) ไม่ใช่ `1` — พิสูจน์ว่า connection เก่าไม่เคยถูกปิดจริง ไม่ใช่แค่ leak ในทางทฤษฎี

**วิธีแก้:** return การเรียก disconnect จาก effect:

```tsx
// src/components/ChatRoomWithCleanup.tsx
import { useEffect } from 'react';

function ChatRoomWithCleanup({ roomId }: { roomId: string }) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect();
    return () => connection.disconnect(); // cleanup: undo the setup
  }, [roomId]);
  return null;
}

declare function createConnection(roomId: string): { connect(): void; disconnect(): void };

export default ChatRoomWithCleanup;
```

```tsx
// src/__tests__/chatroom-cleanup.test.tsx
import { useEffect } from 'react';
import { render, cleanup } from '@testing-library/react';
import { afterEach, expect, test } from 'vitest';

afterEach(cleanup);

function makeConnection(_roomId: string, onTotalChanged: (n: number) => void) {
  return {
    connect() {
      makeConnection.total++;
      onTotalChanged(makeConnection.total);
    },
    disconnect() {
      makeConnection.total--;
      onTotalChanged(makeConnection.total);
    },
  };
}
makeConnection.total = 0;

function ChatRoomWithCleanupTest({ roomId, onTotalChanged }: { roomId: string; onTotalChanged: (n: number) => void }) {
  useEffect(() => {
    const connection = makeConnection(roomId, onTotalChanged);
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]);
  return null;
}

test('an effect WITH cleanup disconnects on unmount, unlike the buggy version above', () => {
  makeConnection.total = 0;
  let total = 0;
  const { unmount } = render(
    <ChatRoomWithCleanupTest roomId="general" onTotalChanged={(n) => { total = n; }} />,
  );
  expect(total).toBe(1);
  unmount();
  expect(total).toBe(0); // cleanup actually ran — the connection closed
});
```

**จับได้โดย:** ไม่มีอะไรอัตโนมัติเลย — ไม่มี compiler error ไม่มี lint rule ไหนตรวจจับ `return` ที่หายไปใน effect มีแค่ test mount/unmount จริง (หรือ subscription ที่ leak ใน production) เท่านั้นที่เผยมันออกมา ดู **[useEffect & Effects](/react/th/hooks/useeffect-and-effects/)** สำหรับการพิสูจน์ลำดับ cleanup แบบเต็ม

### 2. Stale closure ใน effect ของ `setInterval` (วิธีแก้ด้วย `useEffectEvent`)

```tsx
// @expect-error compiles and runs, but the interval never sees a fresh `increment` — see prose
// src/components/Timer.tsx — as generated
function Timer() {
  const [count, setCount] = useState(0);
  const [increment, setIncrement] = useState(1);

  useEffect(() => {
    const id = setInterval(() => {
      setCount((c) => c + increment); // reads increment from the closure
    }, 1000);
    return () => clearInterval(id);
  }, []); // empty deps — the interval is only ever set up once

  return (
    <div>
      <output>{count}</output>
      <button onClick={() => setIncrement((i) => i + 1)}>bump increment</button>
    </div>
  );
}
```

callback ของ interval ปิดทับ `increment` จาก render ที่ effect รันอยู่ ด้วย dependency array ว่าง effect นั้นรันแค่ครั้งเดียว ตอน mount — callback เลยอ้างอิง `increment` **ตอนเริ่มต้น** (`1`) ตลอดไป ไม่ว่าจะกดปุ่มกี่ครั้งก็ตาม

**อาการ — output test จริง** (fake timer พิสูจน์แล้วใน probe):

```text
✓ useEffectEvent reads the latest increment without re-running the effect (no interval reset)

Test Files  1 passed (1)
     Tests  1 passed (1)
```

เจาะจง: หลัง tick หนึ่งครั้งตอน `increment=1` และ tick หนึ่งครั้งตอน `increment=2` เวอร์ชันบั๊กด้านบนยังโชว์ `2` (`0 + 1 + 1`) ไม่ใช่ `3` — การ bump ไม่มีผลกับ interval ที่กำลังรันอยู่เลย

**วิธีแก้:** แยกการอ่านที่ไม่ reactive ออกมาเป็น `useEffectEvent` (React 19.2) ซึ่งเห็น state ล่าสุดเสมอโดยไม่กลายเป็น dependency:

```tsx
// src/components/TimerFixed.tsx
import { useEffect, useEffectEvent, useState } from 'react';

function TimerFixed({ onTick }: { onTick: () => void }) {
  const [count, setCount] = useState(0);
  const [increment, setIncrement] = useState(1);

  const onTickEvent = useEffectEvent(() => {
    setCount((c) => c + increment);
    onTick();
  });

  useEffect(() => {
    const id = setInterval(onTickEvent, 1000);
    return () => clearInterval(id);
  }, []);

  return (
    <div>
      <output data-testid="count">{count}</output>
      <button onClick={() => setIncrement((i) => i + 1)}>bump increment</button>
    </div>
  );
}

export default TimerFixed;
```

```tsx
// src/__tests__/timer-fixed.test.tsx
import { useEffect, useEffectEvent, useState } from 'react';
import { act, render, cleanup } from '@testing-library/react';
import { afterEach, expect, test, vi } from 'vitest';

afterEach(cleanup);

function TimerFixed({ onTick }: { onTick: () => void }) {
  const [count, setCount] = useState(0);
  const [increment, setIncrement] = useState(1);

  const onTickEvent = useEffectEvent(() => {
    setCount((c) => c + increment);
    onTick();
  });

  useEffect(() => {
    const id = setInterval(onTickEvent, 1000);
    return () => clearInterval(id);
  }, []);

  return (
    <div>
      <output data-testid="count">{count}</output>
      <button onClick={() => setIncrement((i) => i + 1)}>bump increment</button>
    </div>
  );
}

test('useEffectEvent reads the latest increment without re-running the effect (no interval reset)', () => {
  vi.useFakeTimers();
  const onTick = vi.fn();
  const { getByTestId, getByRole } = render(<TimerFixed onTick={onTick} />);

  act(() => { vi.advanceTimersByTime(1000); }); // tick with increment=1
  expect(getByTestId('count').textContent).toBe('1');

  act(() => { getByRole('button').click(); }); // increment becomes 2

  act(() => { vi.advanceTimersByTime(1000); }); // tick with increment=2, SAME interval
  expect(getByTestId('count').textContent).toBe('3'); // 1 + 2, not reset

  vi.useRealTimers();
});
```

**จับได้โดย:** ไม่มีอะไรอัตโนมัติจับบั๊กอ่านค่า-stale ตัวนี้เอง — มีแค่ test แบบ timer จริงเท่านั้น ความผิดพลาด*ตรงข้าม*กัน (การเติม Effect Event เข้า deps array) ถูกจับโดย `react-hooks/exhaustive-deps` พิสูจน์แล้วใน **[useEffect & Effects](/react/th/hooks/useeffect-and-effects/)**

### 3. Hook ที่ถูกเรียกแบบ conditional

```tsx
// @expect-error real eslint error — see prose
// src/components/Toggle.tsx — as generated
import { useState } from 'react';

export function Toggle({ show }: { show: boolean }) {
  if (show) {
    const [on, setOn] = useState(false); // hook called conditionally
    return <button onClick={() => setOn(!on)}>{String(on)}</button>;
  }
  return null;
}
```

Hook ต้องถูกเรียกในลำดับเดียวกันเป๊ะทุก render — hook ข้างใน `if` รันบาง render ไม่รันบาง render ซึ่งทำให้ bookkeeping ภายในของ hook-slot ของ React ไม่ตรงกันทันทีที่ `show` เปลี่ยน

**อาการ — output จริงของ `eslint-plugin-react-hooks@7.1.1`** (flat config `recommended-latest`):

```text
Toggle.tsx
  5:25  error  React Hook "useState" is called conditionally. React Hooks must be called
  in the exact same order in every component render. Did you accidentally call a React
  Hook after an early return?  react-hooks/rules-of-hooks
```

**วิธีแก้:** เรียก hook แบบ unconditional ที่ top level แล้ว branch ที่ *ค่า* แทนการเรียก hook:

```tsx
// src/components/ToggleFixed.tsx
import { useState } from 'react';

export function ToggleFixed({ show }: { show: boolean }) {
  const [on, setOn] = useState(false); // always called, same order every render
  if (!show) return null;
  return <button onClick={() => setOn(!on)}>{String(on)}</button>;
}
```

**จับได้โดย:** กฎ `rules-of-hooks` ของ `eslint-plugin-react-hooks` จับได้เชื่อถือได้ ทันทีที่มันถูกต่อสายเข้า CI จริง — ไม่ใช่โดย `tsc`

### 4. `useRef()` แบบไม่มีค่าเริ่มต้น ภายใต้ typing ของ React 19

```tsx
// @expect-error real tsc error — see prose
// src/BadUseRefNoArg.tsx
import { useRef } from 'react';
function Box() {
  const ref = useRef<HTMLDivElement>(); // React 19 types: no zero-arg overload
  return <div ref={ref} />;
}
```

`@types/react@19` ประกาศ overload ของ `useRef` ไว้เป๊ะ ๆ สามแบบ และไม่มีสักแบบที่รับศูนย์ argument — นิสัยเก่า "ไม่มี argument, `undefined` โดยนัย" จาก type definition รุ่นก่อนไม่ตรงกับ overload ไหนเลย

**อาการ — output จริงของ `tsc`:**

```text
BadUseRefNoArg.tsx(3,15): error TS2554: Expected 1 arguments, but got 0.
```

**วิธีแก้:** ส่งค่าเริ่มต้นแบบชัดเจน — `null` สำหรับ DOM ref ที่จะแปะทีหลัง:

```tsx
// src/UseRefFix.tsx
import { useRef } from 'react';

export function Box() {
  const ref = useRef<HTMLDivElement>(null); // React 19: explicit initial value required
  return <div ref={ref} />;
}
```

**จับได้โดย:** `tsc --noEmit` ทันทีและไม่มีเงื่อนไข — นี่คือ type error จริง ปัจจุบัน ภายใต้ `@types/react@19` ไม่ใช่ style nitpick ดู **[TypeScript with React](/react/th/tooling-and-production/typescript-with-react/)**

### 5. `forwardRef` ในโค้ด React 19 ใหม่

```jsx
// src/components/FancyInputOld.jsx — as generated
import { forwardRef } from 'react';

const FancyInput = forwardRef(function FancyInput(props, ref) {
  return <input {...props} ref={ref} />;
});

export default FancyInput;
```

โค้ดนี้ยังทำงานได้ — `forwardRef` ไม่ถูกลบออก — แต่โค้ดที่ generate มาแล้วเอื้อมไปหามันใน codebase React 19 ถือว่าล้าสมัย ไม่ใช่แค่ "แบบเก่า ๆ" react.dev ตอนนี้ระบุแผนการ deprecate ที่เป็นรูปธรรม ไม่ใช่แค่ "ไม่จำเป็นอีกต่อไป":

> `forwardRef` will be deprecated in a future release.
> — [react.dev/reference/react/forwardRef](https://react.dev/reference/react/forwardRef)

ประวัติ URL ของหน้า reference ของมันเองเป็นสัญญาณอิสระตัวที่สองของการเปลี่ยนแปลงแบบเดียวกัน: **[react.dev/reference/react-dom/hooks/useFormState](https://react.dev/reference/react-dom/hooks/useFormState)** — API ที่เปลี่ยนชื่อในลักษณะคล้ายกัน entry 21 ด้านล่าง — ตอนนี้ redirect ตรงไปหน้า replacement เลย เป็นการปฏิบัติแบบเดียวกับที่ docs ของ `forwardRef` เองกำลังมุ่งไป

**วิธีแก้:** รับ `ref` เป็น prop ธรรมดา — ไม่มี wrapper ไม่มีการเต้น generic-parameter แยกต่างหาก:

```tsx
// src/components/FancyInputNew.tsx
type FancyInputProps = { placeholder?: string; ref?: React.Ref<HTMLInputElement> };

function FancyInputNew({ placeholder, ref }: FancyInputProps) {
  return <input placeholder={placeholder} ref={ref} />;
}

export default FancyInputNew;
```

**จับได้โดย:** ไม่มีอะไรอัตโนมัติ — `forwardRef` ยัง compile และทำงานได้วันนี้ มีแค่การอ่าน timeline ที่ react.dev ระบุไว้เอง (หรือ lint rule ของ project ที่ห้ามใช้มัน ถ้ามีตั้งไว้) เท่านั้นที่ตีธง ดู **[useRef & the DOM](/react/th/hooks/useref-and-the-dom/)**

### 6. Selector ของ `useSyncExternalStore` ที่ return object ใหม่ทุกครั้ง

```tsx
// @expect-error real infinite-loop console output — see prose
// src/components/BadSelector.tsx — as generated
import { useSyncExternalStore } from 'react';

function getSnapshotBad() {
  return { count: state.count }; // a NEW object every single call
}

function BadSelectorConsumer() {
  const snap = useSyncExternalStore(subscribe, getSnapshotBad);
  return <span>{snap.count}</span>;
}
```

React เทียบผลลัพธ์ `getSnapshot()` ที่ต่อเนื่องกันด้วย `Object.is` เพื่อตัดสินว่ามีอะไรเปลี่ยนไหม `getSnapshot` ที่ return object literal ใหม่ทุกครั้งไม่มีทางถูกมองว่า "ไม่เปลี่ยน" ได้เลย — แม้ state ข้างในจะเหมือนเดิมทุกประการ — React เลย re-render, เรียก `getSnapshot` อีกที ได้ object ใหม่อีกตัว แล้ว re-render อีก ไปเรื่อย ๆ

**อาการ — console output จริง คำต่อคำ:**

```text
The result of getSnapshot should be cached to avoid an infinite loop
```

ตามด้วย safety limit ของ render-depth ของ React เองที่ throw `Maximum update depth exceeded`

**วิธีแก้:** return primitive หรือ cache object ที่ derive ไว้ให้การเรียกซ้ำกับ state เดียวกัน return reference เดิม:

```tsx
// src/components/GoodSelector.tsx
import { useSyncExternalStore } from 'react';

function getSnapshotGood() {
  return state.count; // a primitive — always comparable by value
}

export function GoodSelectorConsumer() {
  const count = useSyncExternalStore(subscribe, getSnapshotGood);
  return <span>{count}</span>;
}

declare const state: { count: number };
declare function subscribe(cb: () => void): () => void;
```

**จับได้โดย:** ไม่มีอะไรตอน type-check — มีแค่การรัน component จริงเท่านั้นที่เผย warning แล้วตามด้วย error ที่ throw ดู **[External Stores](/react/th/state-and-data/external-stores/)** สำหรับการพิสูจน์เต็มรูปแบบ

### 7. `use()` ถูกเรียกด้วย promise ที่สร้างสด ๆ ตอน render

```tsx
// @expect-error suspends forever / refetches every render — see prose
// src/components/SearchResultsBad.tsx — as generated
function SearchResultsBad({ query }: { query: string }) {
  const resultsPromise = fetchResults(query); // a NEW promise every render
  const results = use(resultsPromise);
  return <ul>{results.map((r) => <li key={r.id}>{r.title}</li>)}</ul>;
}

declare function fetchResults(query: string): Promise<{ id: string; title: string }[]>;
declare function use<T>(p: Promise<T>): T;
```

`use()` ไม่ fetch หรือ cache อะไรเลย — มันแค่อ่าน promise ไหนก็ตามที่คุณส่งให้ การเรียก `fetchResults(query)` ตรง ๆ ข้างใน render body สร้าง promise ใหม่เอี่ยมทุก render component เลยหรือ suspend ไม่จบ (ถ้าการ retry ของ `use()` เจอ promise ใหม่ที่ไม่เคย resolve ทันเวลาซ้ำ ๆ) หรือไม่ก็ fetch ใหม่ทุก render เดียว

**วิธีแก้:** cache promise ต่อ `query` และยกเลิก request ที่ค้างอยู่ก่อนหน้าเมื่อ `query` เปลี่ยน:

```tsx
// src/components/SearchResultsFixed.tsx
const cache = new Map<string, Promise<{ id: string; title: string }[]>>();

function getResultsPromise(query: string) {
  if (!cache.has(query)) cache.set(query, fetchResults(query));
  return cache.get(query)!;
}

function SearchResultsFixed({ query }: { query: string }) {
  const results = use(getResultsPromise(query)); // stable reference per query
  return <ul>{results.map((r) => <li key={r.id}>{r.title}</li>)}</ul>;
}

declare function fetchResults(query: string): Promise<{ id: string; title: string }[]>;
declare function use<T>(p: Promise<T>): T;
```

**จับได้โดย:** ไม่มีอะไรอัตโนมัติ — ไม่มี compiler error ไม่มี lint rule มีแค่พฤติกรรมที่สังเกตได้ (spinner โหลดค้างตลอดไป หรือ network tab เต็มไปด้วย request ซ้ำ) เท่านั้นที่เผยมัน ดู **[`use()` & Data Fetching](/react/th/concurrent-and-suspense/use-and-data-fetching/)** สำหรับการพิสูจน์เรื่อง timing ว่าทำไม promise ต้องถูกสร้างนอก render ตั้งแต่แรก

### 8. `useFormState` แทนที่จะเป็น `useActionState`

```tsx
// src/components/ChangeNameOld.tsx — as generated
'use client';
import { useFormState } from 'react-dom';

function ChangeNameOld() {
  const [error, formAction] = useFormState(updateNameAction, null);
  return (
    <form action={formAction}>
      <input name="name" />
      {error && <p>{error}</p>}
    </form>
  );
}

declare function updateNameAction(prevState: string | null, formData: FormData): Promise<string | null>;

export default ChangeNameOld;
```

## Server/client boundary กับ directive

### 9. Hook ที่ใช้ในไฟล์ที่ไม่มี directive `'use client'`

```tsx

  return <button onClick={() => setCount((c) => c + 1)}>{count}</button>;
}
```

ไฟล์นี้ compile ผ่านสะอาดภายใต้ `tsc --noEmit` ใน probe Vite ธรรมดาของคอร์สนี้ — `'use client'` เป็นแค่ string literal ในสายตาของ TypeScript และ Vite SPA ไม่มี server/client split ให้ directive นี้มีความหมายตั้งแต่แรกอยู่แล้ว เอาไฟล์เดียวกันนี้ไปวางใน RSC-capable framework จริง (Next.js App Router) โดยไม่มี `'use client'` บนตัวเองหรือ parent build step ของ framework เองจะปฏิเสธมันทันทีที่มันพยายามใช้ client-only hook จากสิ่งที่ framework มองว่าเป็น Server Component

**ข้อจำกัดที่ต้องพูดตรง ๆ:** probe Vite ของคอร์สนี้ reproduce build error ระดับ framework แบบนั้นไม่ได้ — การพิสูจน์เรื่องนี้ต้องการ RSC framework จริง ซึ่งเป็นสิ่งที่ **[Server and Client Components](/nextjs/en/foundations/server-and-client-components/)** ในคอร์ส Next.js Deep Dive ทำ กับ `next build` จริง

**วิธีแก้:** เติม directive เข้าไฟล์ (หรือยืนยันว่า parent มีอยู่แล้ว):

**จับได้โดย:** build step ของ RSC-capable framework จริงเท่านั้น — ไม่ใช่ `tsc` ไม่ใช่ probe ของคอร์สนี้ ดู **[Server Components](/react/th/react-19/server-components/)** สำหรับสิ่งที่ directive นี้บ่งบอกจริง ๆ

### 12. Setter ของ `useOptimistic` ถูกเรียกนอก Transition หรือ Action



### 16. `useEffect` sync state ที่ควรจะ derive ตอน render

```jsx
// src/components/NameFieldsBad.jsx — as generated
```

`fullName` คำนวณได้ทั้งหมดจาก `firstName` กับ `lastName` — มันไม่ต้องการ state หรือ effect ของตัวเองเลย การ sync มันด้วย effect เพิ่ม render เกินมาหนึ่งครั้ง (effect ยิง *หลัง* render แรกด้วย `fullName` เก่า แล้ว re-render ด้วยค่าที่ sync แล้ว) และเพิ่มจุดที่สองที่ทั้งสองค่าจะ drift ไม่ตรงกันได้

```jsx
// src/components/NameFieldsFixed.jsx
```

### 19. Context ถูกใช้เป็น global store ที่เปลี่ยนบ่อย

```tsx
// src/components/CartProvider.tsx — as generated
function CartProvider({ children }: { children: React.ReactNode }) {
  const [items, setItems] = useState<Item[]>([]);
  const [user, setUser] = useState<User | null>(null);

  return (
    <CartContext
      value={{
        items,
        user,
        addItem: (item: Item) => setItems((prev) => [...prev, item]),
      }}
    >
      {children}
    </CartContext>
  );
}

type Item = { id: string };
type User = { id: string };
declare const CartContext: React.Context<{ items: Item[]; user: User | null; addItem: (item: Item) => void }>;
```

object `value` ถูกสร้างแบบ inline ทุก render ของ `CartProvider` — object ใหม่เอี่ยมทุกครั้ง แม้ทั้ง `items` และ `user` จะไม่ได้เปลี่ยนจริง ๆ เลยก็ตาม consumer ทุกตัวของ `CartContext` re-render ทุกครั้งที่ `CartProvider` re-render ไม่ว่าจะด้วยเหตุผล*อะไรก็ตาม* และ `memo` บน consumer พวกนั้นหยุดมันไม่ได้ — React เทียบ `value` ของ provider ด้วย reference และ `memo` มองแค่ prop เท่านั้น ไม่เคยมองที่ context

**อาการ — output test จริง:**

```text

✓ a useMemo'd provider value lets memo bail the consumer out

Test Files  1 passed (1)
     Tests  2 passed (2)
```

parent re-render ที่ไม่เกี่ยวข้องสองครั้ง (tick counter ที่ไม่เกี่ยวข้อง แทนอะไรก็ตามที่เปลี่ยน) ทำให้ consumer ที่ห่อด้วย `memo` re-render สองครั้ง — พิสูจน์เทียบกันด้วย object literal แบบ inline กับตัวที่ผ่าน `useMemo` แล้ว ทุกบรรทัดอื่นเหมือนกันเป๊ะ

**วิธีแก้:** memoize provider value แล้วแยกค่าที่เปลี่ยนเร็วออกเป็น context ของตัวเอง (หรือ external store) แทนที่จะกระจายมันผ่าน provider กว้าง ๆ ตัวเดียวกับข้อมูลที่เปลี่ยนช้า:

```tsx
// src/components/CartProviderFixed.tsx
import { useCallback, useMemo, useState } from 'react';

export function CartProviderFixed({ children }: { children: React.ReactNode }) {
  const [items, setItems] = useState<Item[]>([]);
  const [user, setUser] = useState<User | null>(null);
  const addItem = useCallback((item: Item) => setItems((prev) => [...prev, item]), []);
  const value = useMemo(
    () => ({ items, user, addItem, setUser }),
    [items, user, addItem, setUser],
  );

  return <CartContext value={value}>{children}</CartContext>;
}

type Item = { id: string };
type User = { id: string };
declare const CartContext: React.Context<{ items: Item[]; user: User | null; addItem: (item: Item) => void }>;
```

**จับได้โดย:** ไม่มีอะไรอัตโนมัติ — ไม่มี warning ไม่มี lint rule สำหรับ context value แบบ inline มีแค่ test นับ render (หรือ Profiler trace) เท่านั้นที่เผยมัน ดู **[Context](/react/th/state-and-data/context/)** และ **[External Stores](/react/th/state-and-data/external-stores/)** สำหรับเวลาที่ควรไปไกลกว่า Context

### 20. `startTransition(async () => {...})` เสีย priority หลัง `await`

```tsx
// @expect-error compiles and runs; the post-await update silently escapes the Transition — see prose
// src/components/SearchResultsBad.tsx — as generated
function SearchResultsBad() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState<string[]>([]);

  function handleChange(nextQuery: string) {
    startTransition(async () => {
      setQuery(nextQuery);
      const data = await fetchResults(nextQuery);
      setResults(data); // looks fine — it's inside startTransition, right?
    });
  }

  return <input onChange={(e) => handleChange(e.target.value)} />;
}

declare function fetchResults(query: string): Promise<string[]>;
```

`setResults(data)` รันหลัง `await fetchResults(nextQuery)` แม้จะอยู่ข้างใน callback `startTransition(async () => {...})` ทาง lexical มันก็**ไม่ใช่**ส่วนหนึ่งของ Transition — react.dev ระบุชัดเจนว่ามีแค่โค้ดก่อน `await` แรกเท่านั้นที่ถูกครอบอัตโนมัติ อะไรก็ตามหลังจากนั้นต้องการ `startTransition` ของตัวเองซ้อนเข้าไปอีกที ถ้า component ที่อ่าน `results` suspend การ update นี้จะโชว์ loading fallback แทนที่จะเก็บผลลัพธ์เก่าไว้บนจอ ซึ่งตรงข้ามกับพฤติกรรมที่ Transition มีไว้ป้องกันเป๊ะ

**อาการ — output test ที่พิสูจน์แล้วจริง** (จาก pattern เดียวกันที่พิสูจน์กับ `Suspense`):

```text
✓ WITHOUT re-wrapping: the update after await is not a Transition, so Suspense shows the fallback immediately
✓ WITH re-wrapping: the update after await stays a Transition, so Suspense keeps the old content until ready
```

**วิธีแก้:** ห่อ update หลัง `await` ด้วย `startTransition` ของตัวเอง:

```tsx
// src/components/SearchResultsFixed.tsx
import { startTransition, useState } from 'react';

export function SearchResultsFixed() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState<string[]>([]);

  function handleChange(nextQuery: string) {
    startTransition(async () => {
      setQuery(nextQuery);
      const data = await fetchResults(nextQuery);
      startTransition(() => setResults(data)); // re-wrapped: stays part of the Transition
    });
  }

  return (
    <div>
      <input value={query} onChange={(e) => handleChange(e.target.value)} />
      <ul>{results.map((r) => <li key={r}>{r}</li>)}</ul>
    </div>
  );
}

declare function fetchResults(query: string): Promise<string[]>;
```

**จับได้โดย:** ไม่มีอะไรอัตโนมัติ — ไม่มี compiler error ไม่มี lint rule มีแค่ test ที่อิง Suspense (หรือ loading flash ที่ user มองเห็นในจุดที่ content เก่าควรจะอยู่) เท่านั้นที่เผยมัน ดู **[Transitions](/react/th/concurrent-and-suspense/transitions/)** และ **[Actions & useActionState](/react/th/react-19/actions-and-useactionstate/)** สำหรับการพิสูจน์เต็มรูปแบบกับ Suspense boundary จริง

ถ้า `userId` เปลี่ยนเร็ว (คลิกไล่ผ่าน list) request ที่เก่ากว่าและช้ากว่าอาจ resolve **หลัง** request ที่ใหม่กว่าและเร็วกว่า แล้ว overwrite state ที่สดด้วยข้อมูลเก่า — ไม่มีอะไรตรงนี้ให้ยกเลิก request ที่ล้าสมัย

**อาการ — output test จริง** (คู่ "ช้าแล้วเร็ว" จำลอง ตัวที่ช้าเริ่มก่อนแต่จะ resolve ทีหลัง):

```text
✓ AbortController prevents the stale (slow) response from overwriting the fresh one

Test Files  1 passed (1)
     Tests  1 passed (1)
```

ถ้าไม่มี abort logic test นี้ล้มเหลวเป๊ะ ๆ: `.then` ของ request ที่ช้ายังยิงหลังตัวที่เร็ว แล้วทิ้ง `name` ไว้ที่ค่าเก่า

**วิธีแก้:** return การเรียก `AbortController.abort()` จาก cleanup แล้ว ignore `AbortError` ที่ตามมา:

```tsx
// src/components/ProfileFixed.tsx
import { useEffect, useState } from 'react';

declare function fetchUser(userId: string, signal: AbortSignal): Promise<string>;

function ProfileFixed({ userId }: { userId: string }) {
  const [name, setName] = useState('loading');
  useEffect(() => {
    const controller = new AbortController();
    fetchUser(userId, controller.signal)
      .then((result) => setName(result))
      .catch((err: Error) => {
        if (err.name !== 'AbortError') throw err;
      });
    return () => controller.abort();
  }, [userId]);
  return <output>{name}</output>;
}

export default ProfileFixed;
```

**จับได้โดย:** ไม่มีอะไรอัตโนมัติ — ไม่มี compiler error ไม่มี lint rule มีแค่ test เรื่อง race condition (หรือ user report ที่ timing-dependent เป็นบางครั้ง) เท่านั้นที่เผยมัน ดู **[useEffect & Effects](/react/th/hooks/useeffect-and-effects/)** สำหรับการพิสูจน์เต็มรูปแบบ

### 22. `Date.now()`/`Math.random()` ถูกอ่านตอน render

```jsx
// @expect-error real hydration mismatch — see prose
// src/components/Timestamp.jsx — as generated

  return <p>rendered at {Date.now()}</p>;
}
```

`Date.now()` (และ `Math.random()`) นิยามตัวเองว่าต่างกันทุกครั้งที่ถูกเรียก Server Component ที่ render มันครั้งเดียวผลิต HTML บางอย่างออกมา ทันทีที่ component เดียวกันนั้นรัน*ซ้ำ*ฝั่ง client เพื่อ hydrate มันเรียก `Date.now()` เป็นครั้งที่สองแล้วได้ค่าที่ต่างออกไป — hydration mismatch แบบตำราตรง ๆ

**อาการ — output จริงของ `hydrateRoot` ที่จับได้** (server render ด้วย timestamp mock ตัวหนึ่ง client hydrate ด้วยอีกตัว ห่างกันห้าวินาที):

```text

- Variable input such as `Date.now()` or `Math.random()` which changes each time it's called.
- Date formatting in a user's locale which doesn't match the server.
- External changing data without sending a snapshot of it along with the HTML.
- Invalid HTML tag nesting.

It can also happen if the client has a browser extension installed which messes with the
HTML before React loaded.

https://react.dev/link/hydration-mismatch

  <Timestamp>
    <p>
+     1700000005000
-     1700000000000
```

ข้อความ error ของ React เองระบุ `Date.now()`/`Math.random()` แบบเจาะจงตรง ๆ ว่าเป็นสาเหตุที่รู้กันอยู่แล้ว — นี่ไม่ใช่การเดา framework กำลังวินิจฉัยอาการของตัวเองอยู่

**วิธีแก้:** คำนวณ timestamp ครั้งเดียว นอกส่วนที่รันทั้งฝั่ง server และ client (ส่งมันเป็น prop จากจุดที่รันครั้งเดียวเท่านั้น) หรือย้ายการอ่านเข้า effect เพื่อให้มันรันแค่ฝั่ง client เท่านั้น หลังจาก hydration reconcile เสร็จแล้ว:

```tsx
// src/components/TimestampFixed.tsx
import { useEffect, useState } from 'react';

  const [time, setTime] = useState<number | null>(null); // null on both server and first client render

    setTime(Date.now()); // only runs on the client, after hydration
  }, []);
  return <p>{time === null ? 'loading…' : `rendered at ${time}`}</p>;
}

export default TimestampFixed;
```

### 23. `useLayoutEffect` อ่านค่าที่ `useEffect` ตัวพี่น้องกำลังเขียนอยู่

```tsx
// @expect-error compiles and runs, but the read is always one commit stale — see prose
// src/components/Backwards.tsx — as generated
function Backwards({ expand }: { expand: boolean }) {
  const boxRef = useRef<HTMLDivElement>(null);
  const [measuredWidth, setMeasuredWidth] = useState(-1);

  // WRITE happens here — useEffect fires AFTER the browser paints.
  useEffect(() => {
    if (boxRef.current) boxRef.current.style.width = expand ? '200px' : '100px';
  }, [expand]);

  // READ happens here — useLayoutEffect fires BEFORE the browser paints,
  // strictly before the sibling useEffect above, on the SAME commit.
  useLayoutEffect(() => {
    if (boxRef.current) setMeasuredWidth(parseInt(boxRef.current.style.width || '0', 10));
  });

  return (
    <div>
      <div ref={boxRef} style={{ width: '100px' }} />
      <span>{measuredWidth}</span>
    </div>
  );
}
```

`useLayoutEffect` ยิง**ก่อน**`useEffect`เสมอ ในทุก commit เดียวกัน — ลำดับนี้พิสูจน์แล้ว ไม่ใช่เรื่องบังเอิญ component ที่เขียนค่าใน `useEffect` แล้วอ่านมันกลับใน `useLayoutEffect` หวังจะเห็น write ของ commit ตัวเอง โดยโครงสร้างแล้วรับประกันว่าจะอ่านสิ่งที่ commit *ก่อนหน้า* เขียนไว้ล่าสุดแทน

**อาการ — output ของ log ที่เรียงลำดับ จริง:**

```text
✓ useLayoutEffect fires before useEffect, on the SAME commit — a read in useLayoutEffect always predates a write in useEffect

Test Files  1 passed (1)
     Tests  1 passed (1)
```

พิสูจน์ด้วย log array ธรรมดา ข้ามทั้ง mount และการ re-render ครั้งถัดมา: `['layout-effect (read runs here)', 'effect (write runs here)']` ลำดับนี้ทุก commit เดียว — ไม่เคยกลับกัน

**วิธีแก้:** ย้ายการอ่านเข้า `useEffect` ด้วย (phase เดียวกับ write ที่มันขึ้นกับ) หรือปรับโครงสร้างให้ layout effect เขียนของตัวเองตรง ๆ โดยไม่ขึ้นกับ passive effect ของตัวพี่น้อง:

```tsx
// src/components/BackwardsFixed.tsx
import { useEffect, useRef, useState } from 'react';

export function BackwardsFixed({ expand }: { expand: boolean }) {
  const boxRef = useRef<HTMLDivElement>(null);
  const [measuredWidth, setMeasuredWidth] = useState(-1);

  useEffect(() => {
    if (!boxRef.current) return;
    boxRef.current.style.width = expand ? '200px' : '100px';
    setMeasuredWidth(parseInt(boxRef.current.style.width, 10)); // same phase as the write
  }, [expand]);

  return (
    <div>
      <div ref={boxRef} style={{ width: '100px' }} />
      <span>{measuredWidth}</span>
    </div>
  );
}
```

### 24. Object หรือ function literal แบบ inline ทำลาย `React.memo`

```jsx
// src/components/RowBad.jsx — as generated
const Row = React.memo(function Row({ style }) {
  return <li style={style}>{style.label}</li>;
});

function List({ items }) {
  return (
    <ul>
      {items.map((item) => (
        <Row key={item.id} style={{ color: item.color, label: item.text }} />
      ))}
    </ul>

}
```

`Row` ถูกห่อด้วย `React.memo` แต่ทุกจุดที่เรียกมันสร้าง object literal `{ color, label }` ใหม่เอี่ยมทุก render ของ `List` — ทำให้การเทียบ prop แบบ shallow ของ `Row` เห็น prop `style` ว่า "ต่างกัน" เสมอ แม้ `item.color`/`item.text` จะไม่เปลี่ยนแปลงเลยก็ตาม `React.memo` ไม่เคยมีโอกาสข้ามอะไรเลย

**อาการ — output test จริง:**

```text
✓ a new object literal passed as a prop defeats React.memo — the child re-renders every time
✓ a stable object reference lets React.memo actually skip re-renders

Test Files  1 passed (1)
     Tests  2 passed (2)
```

parent re-render สามครั้งผลิต child re-render สามครั้งกับเวอร์ชัน inline-object และ child re-render แค่ครั้งเดียวข้าม parent re-render สามครั้งเดียวกันนั้น ทันทีที่ object reference ถูกเก็บให้เสถียร — component เดียวกัน เนื้อหา prop เดียวกัน ต่างกันแค่ความเสถียรของ reference

**วิธีแก้:** memoize style object หรือปรับโครงสร้างให้รับ prop แบบ primitive (ซึ่งเทียบกันถูกต้องด้วยค่าโดยไม่มีเรื่อง reference เข้ามาเกี่ยวข้องเลย):

```jsx
const RowFixed = React.memo(function RowFixed({ color, label }) {

        <RowFixed key={item.id} color={item.color} label={item.text} />

  );
}
```
