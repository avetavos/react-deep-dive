## Composition คือ pattern พื้นฐาน

คำตอบของ React สำหรับการ reuse ไม่ใช่ inheritance — คือ **composition** แทนที่จะ extend component คุณส่ง content และ behavior เข้าไป *ข้างใน* มัน รูปแบบที่ง่ายที่สุดคือ prop `children`: component รับ JSX อะไรก็ได้แล้วตัดสินใจว่าจะวางไว้ตรงไหน

```jsx
// A generic Card that doesn't know or care what's inside it.
function Card({ title, children }) {
  return (
    <section className="card">
      <h3>{title}</h3>
      <div className="card-body">{children}</div>
    </section>
  );
}

<Card title="Profile">
  <Avatar user={user} />
  <p>{user.bio}</p>
</Card>
```

## Slot ผ่าน props: มากกว่าแค่ `children`

คุณส่ง JSX ผ่าน prop *ไหนก็ได้* ไม่ใช่แค่ `children` — component ที่มีหลาย region ของ content ที่แยกกันสามารถรับ prop หนึ่งตัวต่อ **slot** typed ให้แต่ละ region รับแค่ content ที่ render ได้เท่านั้น:

```tsx
// src/components/PageLayout.tsx
import type { ReactNode } from 'react';

export function PageLayout({
  sidebar,
  main,
  footer,
}: {
  sidebar: ReactNode;
  main: ReactNode;
  footer?: ReactNode;
}) {
  return (
    <div className="page">
      <aside className="page__sidebar">{sidebar}</aside>
      <main className="page__main">{main}</main>
      {footer && <footer className="page__footer">{footer}</footer>}
    </div>
  );
}
```

```jsx
<PageLayout sidebar={<Nav />} main={<Feed />} footer={<Copyright />} />
```

นี่คือวิธีหลีกเลี่ยง prop-drilling ลึก ๆ และ inheritance tree ที่แข็งทื่อ: แต่ละ slot ก็แค่ prop ธรรมดา จึงถูก type ไว้ optional หรือ required เหมือน prop อื่น ๆ และ layout component ไม่ต้องรู้เลยว่าข้างในมีอะไรจริง ๆ

## Compound component พร้อม typed context

เมื่อ component หลายตัวต้องทำงานร่วมกันและ **share state** pattern *compound component* เปิด family ของชิ้นส่วนที่ประสานกันผ่าน state ที่แชร์ (มักผ่าน context) — ในขณะที่ consumer จัดเรียงมันได้อย่างอิสระ

```jsx
// The consumer composes the pieces; Tabs shares state via context internally.
<Tabs defaultValue="a">
  <TabList>
    <Tab value="a">First</Tab>
    <Tab value="b">Second</Tab>
  </TabList>
  <TabPanel value="a">Panel A</TabPanel>
  <TabPanel value="b">Panel B</TabPanel>
</Tabs>
```

### พิสูจน์: shared state ผ่าน context และ guard ที่ typed กันการใช้ผิด

```tsx
// src/components/Tabs.tsx
import { createContext, useContext, useState, type ReactNode } from 'react';

type TabsContextValue = { active: string; setActive: (value: string) => void };
const TabsContext = createContext<TabsContextValue | null>(null);

function useTabsContext(component: string): TabsContextValue {
  const ctx = useContext(TabsContext);
  if (!ctx) throw new Error(`<${component}> must be rendered inside <Tabs>`);
  return ctx;
}

export function Tabs({ defaultValue, children }: { defaultValue: string; children: ReactNode }) {
  const [active, setActive] = useState(defaultValue);
  return <TabsContext.Provider value={{ active, setActive }}>{children}</TabsContext.Provider>;
}

export function TabList({ children }: { children: ReactNode }) {
  return <div role="tablist">{children}</div>;
}

export function Tab({ value, children }: { value: string; children: ReactNode }) {
  const { active, setActive } = useTabsContext('Tab');
  return (
    <button role="tab" aria-selected={active === value} onClick={() => setActive(value)}>
      {children}
    </button>
  );
}

export function TabPanel({ value, children }: { value: string; children: ReactNode }) {
  const { active } = useTabsContext('TabPanel');
  if (active !== value) return null;
  return <div role="tabpanel">{children}</div>;
}
```

```tsx

    return <Tab value="a">oops</Tab>;

```

`TabsContextValue | null` (แทนที่จะให้ context มีค่า default ปลอม ๆ) คือสิ่งที่ทำให้ guard ของ `useTabsContext` เป็นไปได้ *และ* type-safe: TypeScript บังคับให้ทุกตัวที่อ่านต้องจัดการ case `null` และ error ที่ throw ให้ข้อความที่แม่นยำ action ได้ แทนที่จะเป็น "cannot read property of undefined" ที่งงในชั้นลึกกว่า

## Render prop และทำไม hooks มาแทนที่ส่วนใหญ่

**render prop** คือ prop ที่ค่าของมันเป็น function ที่คืน JSX — ให้ component share *logic* ในขณะที่ caller ควบคุม *การ render*

```jsx
// Render prop: MouseTracker owns the logic, the caller renders.
<MouseTracker render={({ x, y }) => <p>Cursor at {x}, {y}</p>} />
```

Render prop เป็นวิธีคลาสสิกในการ share stateful logic ก่อนมี hooks วันนี้ **custom hook** ทำแบบเดียวกันได้ตรงกว่า — ไม่มี wrapper component ไม่มีการซ้อน:

```jsx
// The modern equivalent: a custom hook.
function Component() {
  const { x, y } = useMousePosition();   // logic shared via a hook
  return <p>Cursor at {x}, {y}</p>;      // caller renders normally
}
```

คุณยัง *เห็น* render prop อยู่ (บาง library ใช้มัน และ `children`-as-a-function ก็เป็นหนึ่งในนั้น) แต่สำหรับ share logic ของตัวเอง ให้หยิบ custom hook ก่อน

### `children` เป็น function typed ด้วย generics

รูปแบบ render-prop ที่ยังอยู่รอดบ่อยที่สุดคือ `children` เองที่เป็น function — มีประโยชน์เมื่อ component ถือ **collection** และต้องการให้ caller ควบคุมว่าแต่ละ item render ยังไง โดยไม่ต้องเสีย type safety ว่า item นั้นคือ *อะไร* จริง ๆ:

```tsx
// src/components/DataList.tsx
import type { ReactNode } from 'react';

export function DataList<T>({
  items,
  children,
}: {
  items: T[];
  children: (item: T, index: number) => ReactNode;
}) {
  return (
    <ul>
      {items.map((item, i) => (
        <li key={i}>{children(item, i)}</li>
      ))}
    </ul>
  );
}
```

```tsx
// src/__tests__/dataListGenerics.test.tsx
import { render, screen } from '@testing-library/react';
import { DataList } from '../components/DataList';

test('DataList<T> infers T from `items` — string items give `item` a string type', () => {
  render(<DataList items={['a', 'b']}>{(item) => <span>{item.toUpperCase()}</span>}</DataList>);
  expect(screen.getByText('A')).toBeTruthy();
  expect(screen.getByText('B')).toBeTruthy();
});

test('DataList<T> infers an object shape from `items` — no cast needed to read its fields', () => {
  const items = [{ id: 1, label: 'One' }, { id: 2, label: 'Two' }];
  render(<DataList items={items}>{(item, index) => <span>{index}:{item.label}</span>}</DataList>);
  expect(screen.getByText('0:One')).toBeTruthy();
  expect(screen.getByText('1:Two')).toBeTruthy();
});
```

สังเกตว่า `item.toUpperCase()` กับ `item.label` พิสูจน์อะไรตรงนี้: เพราะ `DataList` เป็น generic บน `T` TypeScript infer `T` จาก array ที่คุณส่งเป็น `items` แล้ว thread type นั้นเป๊ะ ๆ ไปยัง parameter ของ callback `children` — `string[]` ให้ `.toUpperCase()` ได้โดยไม่ต้อง cast และ object array ให้ `.label` ได้โดยไม่ต้อง cast เช่นกัน ใส่ shape ของ item ผิดแล้วนี่คือ compile error ไม่ใช่ความประหลาดใจตอน runtime

## Polymorphic component: typing `as` prop

component แบบ **polymorphic** render เป็น HTML element (หรือ component) ไหนก็ได้ที่ caller เลือกผ่าน `as` prop โดยยัง type-check prop *เฉพาะ* ของ element นั้น — `<Text as="a" href="...">` ควรต้องการ `href`; `<Text as="button" onClick={...}>` ควรต้องการ `onClick`; `<Text>` เปล่า ๆ ไม่ควรต้องการอันไหนเลย

```tsx
// src/components/PolymorphicText.tsx
import type { ElementType, ComponentPropsWithoutRef, ReactNode } from 'react';

type PolymorphicProps<E extends ElementType> = {
  as?: E;
  children?: ReactNode;
} & Omit<ComponentPropsWithoutRef<E>, 'as' | 'children'>;

export function Text<E extends ElementType = 'span'>({ as, children, ...rest }: PolymorphicProps<E>) {
  const Component = as || 'span';
  return <Component {...rest}>{children}</Component>;
}
```

## Higher-order component: ข้อควรระวังและทำไม hooks มาแทนที่ส่วนใหญ่

**higher-order component (HOC)** คือ function ที่รับ component แล้วคืน component ใหม่ที่ห่อไว้ — วิธีก่อนยุค hooks ในการ share behavior ข้าม component (logging, subscription, prop ที่ inject เข้ามา) มีข้อควรระวังสองอย่างที่เจอบ่อยมากใน HOC code:

1. **Ref forwarding** ref ที่ติดกับ component ที่ถูกห่อต้องถูก thread ผ่าน HOC อย่างชัดเจน — ไม่งั้นมันจะ resolve เป็น `null` แบบเงียบ ๆ สำหรับ caller
2. **Display name** ถ้าไม่มี component ที่ถูก HOC ห่อทุกตัวจะโผล่ใน React DevTools เป็นชื่อ generic ของ wrapper ไม่ใช่ component ที่มันห่อจริง ทำให้ component tree อ่านไม่ออก

```tsx
// src/components/withLogging.tsx
import type { Ref } from 'react';

type InputProps = { placeholder?: string; ref?: Ref<HTMLInputElement> };

function PlainInput({ placeholder, ref }: InputProps) {
  return <input placeholder={placeholder} ref={ref} />;
}

// ❌ Broken: destructures `ref` out along with the rest of props, but never
// passes it anywhere — the caller's ref is silently dropped.
function withLoggingBroken(Wrapped: typeof PlainInput) {
  return function Logged(props: InputProps) {
    const { ref, ...rest } = props;
    return <Wrapped {...rest} />;
  };
}

// ✅ Fixed: forward `ref` straight through — React 19 treats it as a plain
// prop, no forwardRef needed — and set a displayName for DevTools.
function withLoggingFixed(Wrapped: typeof PlainInput) {
  function Logged({ ref, ...rest }: InputProps) {
    return <Wrapped {...rest} ref={ref} />;
  }
  Logged.displayName = `withLogging(${Wrapped.name})`;
  return Logged;
}

export { PlainInput, withLoggingBroken, withLoggingFixed };
```

```tsx
// src/__tests__/hocRefForwarding.test.tsx
import { render } from '@testing-library/react';
import { PlainInput, withLoggingBroken, withLoggingFixed } from '../components/withLogging';

const LoggedBroken = withLoggingBroken(PlainInput);
const LoggedFixed = withLoggingFixed(PlainInput);

test('a HOC that does not forward ref leaves the caller\'s ref null', () => {
  const captured: { current: HTMLInputElement | null } = { current: null };
  render(<LoggedBroken ref={(node) => { captured.current = node; }} />);
  expect(captured.current).toBeNull();
});

test('forwarding ref through the HOC gives the caller the real DOM node', () => {
  const captured: { current: HTMLInputElement | null } = { current: null };
  render(<LoggedFixed ref={(node) => { captured.current = node; }} />);
  expect(captured.current).not.toBeNull();
  expect(captured.current?.tagName).toBe('INPUT');
});

test('the fixed HOC sets a readable displayName instead of the generic wrapper name', () => {
  expect(LoggedFixed.displayName).toBe('withLogging(PlainInput)');
});
```

ข้อควรระวังทั้งสองอย่างคือเหตุผลที่ **hooks มาแทนที่การใช้ HOC ส่วนใหญ่**: custom hook ไม่มี wrapper component เลย จึงไม่มี ref ให้เสียและไม่มี layer เพิ่มให้ต้องตั้งชื่อใน DevTools — logic ข้าม component อยู่ใน hook และ component ที่ใช้มันยังเป็นตัวมันเองเป๊ะ ๆ ใน tree

## Controlled เทียบ uncontrolled

form input เป็น **controlled** เมื่อ React state คือแหล่งความจริงเดียวของมัน (`value` + `onChange`) และเป็น **uncontrolled** เมื่อ DOM ถือค่าไว้และคุณอ่านมันผ่าน ref (หรือใน React 19 จาก `FormData` ของ form ตอน submit)

```jsx
// Controlled: state drives the input; you can validate/transform on every keystroke.
const [name, setName] = useState("");
<input value={name} onChange={(e) => setName(e.target.value)} />

// Uncontrolled: the DOM owns the value; read it when you need it.
const ref = useRef(null);
<input defaultValue="Ada" ref={ref} />   // ref.current.value on submit
```

ใช้ **controlled** เมื่อต้อง react หรือ constrain input ขณะที่มันเปลี่ยน; **uncontrolled** สำหรับ form ง่าย ๆ ที่สนใจแค่ค่าสุดท้าย (state น้อยกว่า re-render น้อยกว่า)

## Mental Model

ทุก pattern ในหน้านี้คือท่าเดียวกัน: ตัดสินใจว่า *ใคร* เป็นเจ้าของแต่ละส่วนของ UI และ *ยังไง* ที่ชิ้นส่วนตกลง contract กัน `children`/slot ยกทั้ง subtree ให้ caller โดยไม่มี contract อะไรเกิน "render อะไรสักอย่าง" Compound component share contract ส่วนตัว (context) ระหว่าง family ของชิ้นส่วนที่กำหนดไว้ `children`-as-a-function กับ polymorphic `as` ผลัก contract เข้าไปใน *ระบบ type* เอง — caller กับ component ตกลงกันชัดเจนว่า shape ของ data หรือ prop อะไรไหลข้าม boundary ตรวจตอน compile แทนที่จะมาเจอตอน runtime HOC พยายาม inject behavior โดย *ไม่มี* contract กับ component ที่ถูกห่อเลย ซึ่งเป็นเหตุผลตรง ๆ ว่าทำไมมันต้องแพตช์มือ (ref forwarding, display name) ที่ hook ไม่ต้องคิดถึงเลย

## ข้อแลกเปลี่ยน

| Pattern | ประโยชน์ | ต้นทุน |
| --- | --- | --- |
| `children` / slot | การ reuse ที่ง่ายที่สุด; caller ควบคุม content เต็มที่ | ไม่มี state ร่วมระหว่างส่วนต่าง ๆ เว้นแต่จะเพิ่ม context |
| Compound component | API declarative สะอาด; share state ไม่มี prop drilling | ชิ้นส่วนผูกกับ context ของ parent เฉพาะตัว; แยกใช้เดี่ยว ๆ ยาก |
| `children` เป็น function (generics) | render ต่อ item แบบ type-safe โดย component เองไม่ต้องรู้อะไรเลย | พิธีรีตองมากกว่า prop `children: ReactNode` ธรรมดาเล็กน้อย |
| Polymorphic `as` prop | component เดียว prop type ถูกต้องสำหรับทุก element ที่มัน render เป็นได้ | กลไก generic type อ่านและดูแลยากพอสมควร |
| Higher-order component | ใช้ได้โดยไม่ต้องมี hooks; ห่อ class component ได้ | ต้องจัดการ ref forwarding และ display name เอง; เพิ่ม wrapper layer |
| Custom hook (แทน HOC) | ไม่มี wrapper component ไม่มีข้อควรระวังเรื่อง ref/display-name | inject markup รอบ caller ไม่ได้ — share ได้แค่ logic/state |

## ความเข้าใจผิดที่พบบ่อย

- **"`children` เป็นทางเดียวในการ compose component"** พิสูจน์แล้วด้านบน: prop ไหนก็ถือ JSX ได้ — slot ผ่าน named prop ก็เป็น composition พอ ๆ กับ `children`
- **"Compound component ต้องใช้ prop drilling เพื่อ share state"** พิสูจน์แล้วด้านบน: ชิ้นส่วน share state ผ่าน context ที่ตั้งครั้งเดียวใน component รากของ family — ไม่ต้อง thread prop เลย
- **"Generic component เสีย type safety พอรับ `children` เป็น function"** พิสูจน์แล้วด้านบน: TypeScript infer type ของ item ที่แน่นอนจาก `items` แล้ว carry เข้าไปใน parameter ของ callback — ไม่มี `any` เข้ามาเกี่ยวข้องเลย
- **"HOC กับ custom hook ใช้แทนกันได้"** HOC ห่อ tree (เพิ่ม markup ได้ และมีข้อควรระวังเรื่อง ref/display-name ต้องจัดการ) hook share แค่ logic กับ state ไม่มีอะไรให้ห่อและไม่มีอะไรให้ forward

## อ่านโค้ดที่ AI เขียน

เมื่อ review code ที่ generate มาที่ใช้ pattern composition เหล่านี้ ให้เช็ก:

- higher-order component destructure แล้วทิ้ง `ref` แทนที่จะ forward มันไหม? ref ของ caller จะเป็น `null` แบบเงียบ ๆ (พิสูจน์แล้วด้านบน)
- component ที่ HOC ห่อมี `displayName` ตั้งไว้ไหม หรือมันจะโผล่ใน React DevTools ภายใต้ชื่อ generic ของ wrapper?
- context ของ compound component ถูก type เป็น non-nullable ด้วยค่า default ปลอม ๆ ซ่อนบั๊ก "ใช้นอก parent" แทนที่จะ throw error ที่ชัดเจนไหม?
- pattern แบบ render-prop หรือ HOC-based แทนที่ด้วย custom hook ธรรมดา เอา wrapper layer ที่ไม่จำเป็นออกได้ไหม?
- component ที่อ้างว่า "polymorphic" (มี `as` prop) re-type prop ของตัวเองต่อ element จริงไหม หรือตกลงมาที่ `any`/prop type หลวมเกินไปที่จะรับ combination ที่ผิดได้ (เช่น `href` บน `button`)?

<SpotTheBug code={`function withAnalytics(Wrapped) {
  function Tracked(props) {
    return <Wrapped {...props} />;
  }
  return Tracked;
}

const TrackedButton = withAnalytics(function Button({ ref, ...props }) {
  return <button ref={ref} {...props} />;
});

function Toolbar() {
  const buttonRef = useRef(null);
  return <TrackedButton ref={buttonRef} onClick={() => buttonRef.current.focus()} />;
}`}>
`Tracked` spread `{...props}` เข้า `Wrapped` แต่ `ref` **ไม่ใช่** prop ธรรมดาที่การ spread จะส่งต่อให้อัตโนมัติแบบ prop จริง — `Tracked` เองไม่เคยประกาศ `ref` ใน parameter list ของตัวเองเลย ดังนั้น `ref` ที่ให้กับ `<TrackedButton ref={buttonRef} />` ถูกติดกับ `Tracked` ไม่ได้ thread ผ่านไปยัง `Button` ข้างใน `buttonRef.current` จบลงที่ชี้ไปยังอะไรก็ตามที่ `Tracked` expose (ไม่มีอะไรเลย เพราะมันเป็น function component ธรรมดาที่ไม่ประกาศ `ref` prop) แทนที่จะเป็น `<button>` DOM node จริง `buttonRef.current.focus()` จึง throw ทางแก้คือให้ `Tracked` รับและ forward `ref` อย่างชัดเจน เหมือน `withLoggingFixed` ด้านบนเป๊ะ: `function Tracked({ ref, ...props }) { return <Wrapped {...props} ref={ref} />; }`
</SpotTheBug>

<Callout title="สรุปหนึ่งบรรทัด">
React reuse ผ่าน **composition** ไม่ใช่ inheritance — `children` และ named slot prop ยก content ให้ component โดยไม่มี contract อะไรเกิน "render อะไรสักอย่าง" **Compound component** share state ผ่าน context ให้ family ของชิ้นส่วนประสานกันได้โดยไม่มี prop drilling เลย — พิสูจน์แล้วด้านบน รวมถึง guard แบบ typed กันการใช้ชิ้นส่วนนอก parent ของมัน **`children` เป็น function** และ **polymorphic `as` prop** ผลัก contract นั้นเข้าไปในระบบ type เอง ทั้งคู่พิสูจน์แล้วด้านบนด้วย generic inference จริง **Higher-order component** ยังใช้ได้แต่ต้องจัดการ ref-forwarding กับ `displayName` เอง — พิสูจน์แล้วด้านบน — ซึ่งเป็นเหตุผลตรง ๆ ว่าทำไม **custom hook** มาแทนที่การใช้งานส่วนใหญ่ของมัน และ input เป็น **controlled** (state คือแหล่งความจริง) หรือ **uncontrolled** (DOM คือแหล่งความจริง)
</Callout>
