ศัพท์ของ React เพิ่มขึ้นเรื่อย ๆ — `useEffectEvent` กับ `<Activity>` มาใน 19.2 ส่วน `<ViewTransition>` กับ `addTransitionType` มาใน 19.3 และตอนนี้ `forwardRef` ก็อยู่บนเส้นทางที่ประกาศไว้แล้วว่าจะ deprecate เวลาอ่านบทเรียนแล้วเจอคำที่ไม่คุ้น หรือไม่แน่ใจว่ายังใช้ได้อยู่กับ React 19.3 ไหม ให้กลับมาดูที่นี่ เราคง term ภาษาอังกฤษไว้ตามที่ developer ใช้จริง แล้วอธิบายความหมายเป็นภาษาไทย

## A

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| act | helper ของ React/RTL ที่ flush การ render, effect และ microtask ให้เสร็จก่อนที่ assertion จะรัน ทำให้ test เห็น DOM แบบเดียวกับที่ browser จะเห็นหลัง update นิ่งแล้ว — `render`/`fireEvent`/`userEvent` จาก Testing Library ห่อ act ให้เราอยู่แล้วในแทบทุกกรณีที่คอร์สนี้เขียน | [Testing](/react/th/tooling-and-production/testing/) |
| Actions | async function ที่ส่งให้ `<form action={fn}>` (หรือส่งให้ `startTransition`) React จะเรียกมันพร้อม `FormData` ที่ผู้ใช้กรอก จัดการ pending state ให้ และ reset field ที่เป็น uncontrolled ให้อัตโนมัติเมื่อสำเร็จ — ไม่ต้องมี `onSubmit`, `preventDefault` หรือประกอบ `FormData` เอง | [Actions & useActionState](/react/th/react-19/actions-and-useactionstate/) |
| `<Activity>` | component จาก React 19.2 ที่ซ่อน subtree ด้วย `display: none` พร้อมเลิก (tear down) Effect ของมันเหมือนกับ unmount จริง ๆ — แต่ต่างจาก unmount ตรงที่ state ยังอยู่ ดังนั้นเมื่อกลับมา `mode="visible"` ทีหลัง ค่า `useState` เดิมจะยังอยู่ครบ พร้อม Effect ที่ setup ใหม่ | [Activity & View Transitions](/react/th/react-19/activity-and-view-transitions/) |
| addTransitionType | ติดชื่อ (เช่น `"submit-comment"`) ให้ Transition ที่กำลังรันอยู่ เพื่อให้ prop `enter`/`exit`/`update` ของ `<ViewTransition>` ตอบสนองต่างกันได้ตามว่า Transition ไหนเป็นต้นเหตุของ update นั้น ถ้าเรียกนอก `startTransition` มันยังใส่ type ให้อยู่ดี แต่จะขึ้น warning | [Activity & View Transitions](/react/th/react-19/activity-and-view-transitions/) |

## B–C

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| batching | การที่ React รวม `setState` หลายครั้งจาก event เดียวกันให้เหลือ re-render รอบเดียว ตั้งแต่ React 18 เรื่องนี้เกิดอัตโนมัติทุกที่ ทั้งใน promise, `setTimeout` และ event handler ของ browser เอง ไม่ใช่แค่ใน event handler แบบ synchronous ของ React — เรียก setter สามครั้งใน handler เดียวก็ยังได้ render แค่รอบเดียว | [useState & Updates](/react/th/hooks/usestate-and-updates/) |
| cacheSignal | API จาก React 19.2 ที่ใช้ได้บน server เท่านั้น คืน `AbortSignal` ที่ยิงขึ้นเมื่อ React render เสร็จแล้ว ทำให้ fetch หรือ database call ที่อยู่ใน scope ของ `cache()` ยกเลิกตัวเองได้แทนที่จะทำงานต่อไปแบบไม่มีประโยชน์ — ใน Client Component มันคืน `null` เสมอ | [use() & Data Fetching](/react/th/concurrent-and-suspense/use-and-data-fetching/) |
| children | prop ที่เก็บเนื้อหาที่ถูกวางซ้อนไว้ใน JSX tag — เป็น `undefined` ถ้าไม่มีลูกเลย, เป็นค่าดิบ ๆ ถ้ามีลูกเดียว หรือเป็น array ถ้ามีตั้งแต่สองขึ้นไป — อย่าสมมติว่ามันเป็น array เสมอ | [JSX & Elements](/react/th/foundations/jsx-and-elements/) |
| commit phase | ครึ่งหลังของการ update: React เทียบ element tree ใหม่กับอันเก่า แล้วใช้เฉพาะการเปลี่ยนแปลง DOM ที่ reconciliation หาเจอ — เป็น phase เดียวที่ side effect (การเขียน DOM จริง) ทำได้ | [Rendering & Reconciliation](/react/th/foundations/rendering-and-reconciliation/) |
| component | function ที่รับ props (input แบบอ่านอย่างเดียวจาก parent) และ state ของตัวเอง แล้วคืนคำอธิบายของ UI — component เดียวกัน เรียกด้วย props/state ต่างกัน ต้องให้ output ต่างกันแบบแน่นอน (deterministic) ความแน่นอนนี้แหละที่ reconciliation และ compiler ต่างก็พึ่งพา | [Why React & the Model](/react/th/foundations/why-react-and-the-model/) |
| `ComponentProps` | utility type ของ TypeScript ที่ "ขโมย" prop type ของ host element (หรือ component อื่น) มาใช้ — `React.ComponentProps<'button'>` ให้ prop ที่ถูกต้องของ `<button>` ทุกตัวโดยไม่ต้องเขียน type เองใหม่ | [TypeScript with React](/react/th/tooling-and-production/typescript-with-react/) |
| composition | กลไกการนำกลับมาใช้ใหม่ของ React แทนที่จะใช้ inheritance: ส่งเนื้อหาหรือพฤติกรรม *เข้าไปใน* component (ผ่าน `children` หรือ prop ที่เป็น slot ตั้งชื่อไว้) แทนการสืบทอด — component แบบทั่วไปไม่จำเป็นต้องรู้เลยว่ามันได้อะไรมา | [Composition Patterns](/react/th/performance-and-patterns/composition-patterns/) |
| compound components | กลุ่ม component (เช่น `<Tabs><Tab/><TabPanel/></Tabs>`) ที่ประสานงานกันผ่าน state ที่ใช้ร่วมกัน มักผ่าน context โดยผู้ใช้จัดวางชิ้นส่วนได้อิสระ — pattern นี้อยู่เบื้องหลัง library อย่าง Radix และ Headless UI | [Composition Patterns](/react/th/performance-and-patterns/composition-patterns/) |
| Context / `<Context>` เป็น provider | ให้ parent ส่งค่าไปถึง descendant ทุกตัวได้โดยไม่ต้องส่ง prop ผ่านทุกชั้น ตั้งแต่ React 19 render context object ตรง ๆ เป็น provider ได้เลย (`<ThemeContext value={theme}>`) ไม่ต้องมี `.Provider` แม้ว่ารูปแบบเดิมจะยังใช้ได้อยู่ก็ตาม | [Context](/react/th/state-and-data/context/) |
| controlled / uncontrolled | input แบบ controlled คือ value ถูกขับเคลื่อนด้วย React state (`value` + `onChange`) ส่วน uncontrolled คือ value อยู่ใน DOM เอง (`defaultValue` แล้วอ่านผ่าน ref หรือ `FormData`) ทั้งสองแบบใช้ได้ทั้งคู่ — กติกาที่สำคัญคือห้ามสลับแบบให้ input เดิมระหว่างที่มันยังอยู่ ไม่งั้น React จะขึ้น console warning จริง ๆ | [Lifting State & Composition](/react/th/state-and-data/lifting-and-composition/) |

## D–H

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| derived state | ค่าที่คำนวณตรงจาก props/state ที่มีอยู่แล้วตอน render (`const fullName = first + ' ' + last`) แทนที่จะ mirror ลง state ของตัวเองผ่าน `useEffect` ที่คอย sync — แบบ derived ไม่มีทางเก่า (stale) และไม่เสีย render เพิ่มเลย | [Lifting State & Composition](/react/th/state-and-data/lifting-and-composition/) |
| effect cleanup | function ที่ effect คืนกลับมา รันก่อน setup รอบถัดไปของ effect เดียวกัน (ตอน dependency เปลี่ยน) และตอน unmount เพื่อยกเลิกสิ่งที่ effect เพิ่งตั้งไว้พอดี — ตัด connection, เคลียร์ timer, ถอด listener การลืมเขียนส่วนนี้คือสาเหตุอันดับหนึ่งของ connection ซ้ำซ้อนกับ memory leak | [useEffect & Effects](/react/th/hooks/useeffect-and-effects/) |
| element | object ธรรมดา ราคาถูก และ immutable ที่ JSX compile ออกมาเป็น (`$$typeof`, `type`, `key`, `props`) — มันคือ *คำอธิบาย* ของ UI ไม่ใช่ DOM node ที่มีชีวิตจริง state ของ component instance ต่างหากที่ reconciliation พยายามรักษาไว้ ข้าม element ที่ถูกสร้างทิ้งใหม่ทุก render | [JSX & Elements](/react/th/foundations/jsx-and-elements/) |
| error boundary | class component (`getDerivedStateFromError` + `componentDidCatch`) ที่จับ error ที่ throw ระหว่าง render, lifecycle หรือ constructor ของ component ที่อยู่ข้างใต้มัน แล้วโชว์ fallback แทนที่จะ unmount ทั้งแอป — มันไม่จับ error ใน event handler หรือโค้ด async | [Error Boundaries](/react/th/concurrent-and-suspense/error-boundaries/) |
| eslint-plugin-react-hooks | lint plugin ทางการที่บังคับ Rules of Hooks และตั้งแต่ v6 ยังส่ง diagnostic ของ React Compiler เองมาด้วย (`set-state-in-render`, `immutability`, `purity` และอื่น ๆ) ในรูป ESLint error ธรรมดา จับ mutation ที่ compiler อาจ bail-out เงียบ ๆ ได้ | [Rules & Custom Hooks](/react/th/hooks/rules-and-custom-hooks/) |
| fallback | UI ที่ boundary `<Suspense fallback={...}>` โชว์ตอนที่มี child ข้างในกำลัง suspend — React จะสลับไปโชว์เนื้อหาจริงทันทีที่โค้ดหรือข้อมูลที่รอ resolve เสร็จ | [Suspense & lazy](/react/th/concurrent-and-suspense/suspense-and-lazy/) |
| fiber | หน่วยงานภายในของ React สำหรับ component instance หนึ่งตัวระหว่างรอบ render/commit — เป็นโครงสร้างข้อมูลที่ทำให้ React หยุด, รันต่อ และจัดลำดับความสำคัญของการ render ได้ คอร์สนี้ต้องการแค่ส่วนแบ่ง render/commit ที่อยู่เหนือมัน ส่วนสถาปัตยกรรม fiber เองอยู่ในโมดูล internals | [Rendering & Reconciliation](/react/th/foundations/rendering-and-reconciliation/) |
| flushSync | บังคับให้ state update กับการ commit DOM ของมันเกิดขึ้นแบบ synchronous ก่อนที่บรรทัดถัดไปจะรัน — สำหรับกรณีหายาก (วัดขนาดทันทีหลังเพิ่ม item, dialog สั่งพิมพ์) ที่ต้องการให้ DOM อัปเดตทันที ใช้บ่อยเกินไปจะทำลาย batching และเสียประสิทธิภาพ | [Refs, Portals & Escape Hatches](/react/th/performance-and-patterns/refs-portals-escape-hatches/) |
| HOC (higher-order component) | function ที่รับ component เข้ามาแล้วคืน component ใหม่ที่ห่อไว้ — วิธีแชร์พฤติกรรมข้าม component แบบสมัยก่อนมี hook ปัญหาเรื้อรังสองอย่างของมัน คือลืม forward `ref` กับลืมตั้ง `displayName` นี่แหละคือเหตุผลที่ custom hook เข้ามาแทนที่การใช้ HOC ส่วนใหญ่ | [Composition Patterns](/react/th/performance-and-patterns/composition-patterns/) |
| hook (Rules of Hooks) | กฎสองข้อ — เรียก hook ที่ top level เท่านั้น (ห้ามอยู่ใน condition, loop หรือหลัง early `return`) และเรียกจาก component หรือ hook อื่นเท่านั้น — มีอยู่เพราะ React จับคู่แต่ละการเรียก hook กับ memory slot ตามลำดับการเรียก ถ้าผิดกฎจะเจอ error จริง ๆ "Rendered fewer hooks than expected" ไม่ใช่แค่ lint warning | [Rules & Custom Hooks](/react/th/hooks/rules-and-custom-hooks/) |
| hydrateRoot | จุดเริ่มต้นฝั่ง client ของ React 19 สำหรับเกาะกับ HTML ที่ render มาจาก server แล้ว (ต่างจาก `createRoot` ที่ render ใหม่ตั้งแต่ต้น) ทั้งคู่รับ option `onCaughtError`/`onUncaughtError`/`onRecoverableError` และ `identifierPrefix` เพื่อกันไม่ให้ค่า `useId` ของสองแอปที่แยกกันชนกันบนหน้าเดียว | [Error Boundaries](/react/th/concurrent-and-suspense/error-boundaries/) |
| hydration | ขั้นตอนที่ React ผูก event handler กับ state เข้ากับ HTML ที่ server render มาแล้วในฝั่ง browser โดยใช้ markup เดิมซ้ำแทนที่จะสร้างใหม่ — มันต้องการให้ render รอบแรกของ client ตรงกับผลลัพธ์ของ server เป๊ะ ๆ | [External Stores](/react/th/state-and-data/external-stores/) |
| hydration mismatch | สิ่งที่เกิดขึ้นเมื่อ render รอบแรกของ client ให้ผลลัพธ์ต่างจาก HTML ที่ server render มาให้ React ซ่อมบางกรณีให้อัตโนมัติ (สังเกตได้ผ่าน `onRecoverableError`) แต่ mismatch ไม่เคยฟรี — มันคือสัญญาณว่า render สองรอบของ input เดียวกันให้ผลไม่ตรงกัน | [External Stores](/react/th/state-and-data/external-stores/) |

## I–O

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| isPending | boolean ที่ทั้ง `useTransition` และ `useActionState` คืนออกมา เป็น `true` ตลอดช่วงชีวิตของ update ที่ห่อไว้ — รวมถึงข้าม `await` ใน callback ของ `startTransition` แบบ async ด้วย — ทำให้ปุ่มปิดตัวเองหรือโชว์ "Saving…" ได้โดยไม่ต้องเขียน loading state เอง | [Transitions](/react/th/concurrent-and-suspense/transitions/) |
| JSX (automatic runtime) | syntax sugar ที่ compile ผ่าน automatic runtime สมัยใหม่ ออกมาเป็นการเรียก `jsx(type, props)` ที่ import จาก `react/jsx-runtime` — JSX เป็น expression ของ JavaScript ดังนั้น `{ }` ข้างในมันก็แค่กลับไปเป็น JS ธรรมดา และไม่ต้อง `import React` แค่เพื่อจะใช้มันอีกต่อไป | [JSX & Elements](/react/th/foundations/jsx-and-elements/) |
| key | identity ที่เสถียรและไม่ซ้ำกันในกลุ่มพี่น้อง (ควรเป็น id ของข้อมูล ไม่ใช่ index ของ array สำหรับ list ที่เรียงลำดับใหม่ได้) ที่ให้ reconciliation ติดตามได้ว่า item ไหนคือ item ไหนข้าม render — กลไกเดียวกันนี้ยังใช้เป็นสวิตช์ reset ได้ด้วย เปลี่ยน `key` ของ component เดี่ยว ๆ เพื่อบังคับให้ React ทิ้ง instance เก่าแล้ว mount ตัวใหม่ | [Rendering & Reconciliation](/react/th/foundations/rendering-and-reconciliation/) |
| lazy | `React.lazy(() => import('./X'))` แบ่ง component ออกเป็น chunk ของตัวเอง โหลดเฉพาะตอนที่มัน render ครั้งแรก แล้ว suspend จนกว่า chunk จะมาถึง — import ที่ล้มเหลวจะถูก cache ไว้ใน instance ของ `lazy()` ตัวนั้นตลอดไป ดังนั้นการ retry ต้องเรียก `lazy()` ใหม่ ไม่ใช่แค่ re-render ตัวเดิม | [Suspense & lazy](/react/th/concurrent-and-suspense/suspense-and-lazy/) |
| lifting state up | ย้าย state ที่ใช้ร่วมกันไปไว้ที่ ancestor ร่วมที่ใกล้ที่สุดของ component ที่ต้องการมัน ทำให้มี single source of truth ตัวเดียว แล้วทั้งสอง component อ่าน/อัปเดตผ่าน props — เป็นทางแก้เริ่มต้นเมื่อ component สองตัวต้องซิงก์กัน | [Lifting State & Composition](/react/th/state-and-data/lifting-and-composition/) |
| memo | `React.memo(Component)` ข้ามการ re-render component เมื่อ props ของมัน shallow-equal กับ render ก่อนหน้า — มันจะได้ผลก็ต่อเมื่อทุก prop มี reference เสถียรเท่านั้น ดังนั้น object/array/function prop แบบ inline ใหม่ทุกครั้งจะทำลายมันทุกครั้งเช่นกัน | [Memoization & the Compiler](/react/th/hooks/memoization-and-the-compiler/) |
| Object.is bail-out | การเทียบค่าแบบเดียวกัน (`===` ที่แก้ edge case ของ `NaN`/`-0` แล้ว) ที่ React ใช้ตัดสินว่า `setState` ครั้งนี้ต้อง render ใหม่ไหม — ตั้งค่าเดิมซ้ำ React จะข้าม render ไปเลย และเพราะมันเป็นการเทียบ reference การ mutate object แล้วส่ง reference เดิมกลับไปก็จะทำให้ข้าม render เหมือนกัน ทั้งที่ข้อมูลเปลี่ยนจริง | [State Snapshot & Purity](/react/th/foundations/state-snapshot-and-purity/) |
| onCaughtError / onUncaughtError / onRecoverableError | ตั้งแต่ React 19 เป็น option ที่ส่งให้ `createRoot`/`hydrateRoot` เพื่อสังเกต error ทุกตัวที่ React จัดการแบบรวมศูนย์ — ไม่ว่าจะถูกจับโดย boundary, ไม่มี boundary จับเลย หรือเป็น hydration mismatch ที่ React ซ่อมให้เงียบ ๆ — แทนที่จะพึ่ง `console.error` อย่างเดียว | [Error Boundaries](/react/th/concurrent-and-suspense/error-boundaries/) |

| useEffectEvent | ออกมาเป็น stable ใน React 19.2: ดึงส่วนที่ไม่ reactive ของ effect ออกมาเป็น "Effect Event" ที่อ่านค่า props/state ล่าสุดเสมอ โดยไม่ตัวมันเองเป็น reactive dependency — ทางแก้เวลาต้องการค่าล่าสุดใน effect โดยไม่อยากบังคับให้ effect รันใหม่ทุกครั้งที่ค่านั้นเปลี่ยน | [useEffect & Effects](/react/th/hooks/useeffect-and-effects/) |
| useFormStatus | ให้ component (จาก `react-dom`) อ่านสถานะ pending ของ `<form>` ที่เป็น *parent* ใกล้ที่สุดได้โดยไม่ต้อง prop drilling เลย ต้องเรียกจาก component ที่เป็นลูกของฟอร์ม ไม่ใช่ component ที่ render tag `<form>` เอง ไม่งั้นมันจะรายงาน `pending: false` เงียบ ๆ ตลอด | [Forms & useOptimistic](/react/th/react-19/forms-and-useoptimistic/) |
| useId | สร้าง id string ที่ไม่ซ้ำและปลอดภัยกับ SSR ให้ component instance หนึ่งตัว ตรงกันระหว่าง HTML ที่ server render กับรอบ hydration ของ client — ตัวนับที่เขียนเองหรือ `Math.random()` รับประกันความตรงกันแบบนี้ไม่ได้ มันมีไว้สำหรับ id ของ accessibility attribute ไม่ใช่สำหรับ key ของ list | [useId & Hook อื่น ๆ](/react/th/hooks/useid-and-other-hooks/) |
| useImperativeHandle | กำหนดว่า `ref` ของ parent เรียก method อะไรได้บ้างบน component แทนที่จะเปิด DOM node ดิบ ๆ ออกมาให้ — ตั้งแต่ React 19 มันประกอบกับ `ref`-เป็น-prop ได้ตรง ๆ ไม่ต้องมี wrapper `forwardRef` | [useRef & the DOM](/react/th/hooks/useref-and-the-dom/) |
| useInsertionEffect | ยิงก่อน layout effect ใด ๆ ทั้งหมด เพื่อให้ library แบบ CSS-in-JS แทรก `<style>` tag ได้ก่อนที่ `useLayoutEffect` จะอ่าน layout ที่ขึ้นกับ style นั้น react.dev ระบุตรง ๆ ว่ามันมีไว้สำหรับคนเขียน library CSS-in-JS ไม่ใช่โค้ดแอปทั่วไป | [useId & Hook อื่น ๆ](/react/th/hooks/useid-and-other-hooks/) |
| useLayoutEffect | รันแบบ synchronous หลังจาก React commit การเปลี่ยนแปลง DOM แล้ว แต่ก่อนที่ browser จะ paint ทำให้การวัด layout ของ node ที่เพิ่ง commit แล้วขยับตำแหน่งทันที ไม่กระพริบให้เห็นแบบที่โค้ดเดียวกันใน `useEffect` (ซึ่งรันหลัง paint) อาจเกิดขึ้นได้ | [Refs, Portals & Escape Hatches](/react/th/performance-and-patterns/refs-portals-escape-hatches/) |
| useMemo | cache ค่าที่คืนกลับมาจากการคำนวณที่แพง คำนวณใหม่เฉพาะตอน dependency เปลี่ยน — ถ้าใช้ React Compiler แล้ว ส่วนใหญ่จะถูกใส่ให้อัตโนมัติ ดังนั้น `useMemo` แบบเขียนมือเก็บไว้ใช้กับโค้ดที่ compiler เข้าไม่ถึง หรือจุดที่ profiler ยังชี้ว่ามีปัญหาอยู่ | [Memoization & the Compiler](/react/th/hooks/memoization-and-the-compiler/) |
| useOptimistic | โชว์ผลลัพธ์ที่คาดว่าจะเกิดขึ้นทันที แล้วให้ React ย้อนกลับไปค่าจริงเองอัตโนมัติถ้า action แบบ async ล้มเหลว — ไม่ต้องเขียนโค้ด rollback เอง setter ของมันต้องรันอยู่ใน `startTransition` หรือ Action เท่านั้น ถ้าเรียกจาก event handler ธรรมดา React จะขึ้น warning แล้วค่าจะย้อนกลับทันที | [Forms & useOptimistic](/react/th/react-19/forms-and-useoptimistic/) |
| useReducer | รวม logic การเปลี่ยน state ที่หลายค่าต้องเปลี่ยนพร้อมกันไว้ใน function บริสุทธิ์ตัวเดียว `(state, action) => nextState` โดย dispatch ด้วยการอธิบายว่า *เกิดอะไรขึ้น* แทนที่จะคำนวณค่าถัดไปตรงจุดเรียก — เหมือนกับข้อกำหนดความ pure ของ reducer การ mutate แล้วคืน reference เดิมกลับไป ทำให้ React ข้าม re-render ไปเลยได้ | [useReducer Patterns](/react/th/state-and-data/usereducer-patterns/) |
| useRef | ให้กล่อง `{ current }` ที่ mutate ได้ อยู่รอดข้าม render โดยไม่ trigger render เมื่อมันเปลี่ยน — เหมาะกับค่าที่ต้องจำไว้แต่ไม่ต้องโชว์ (timer id, ค่าก่อนหน้า) และเข้าถึง DOM (focus, วัดขนาด) การอ่านหรือเขียน `ref.current` ระหว่าง render เอง แทนที่จะอยู่ใน event handler หรือ effect ถือเป็น bug จริง ๆ | [useRef & the DOM](/react/th/hooks/useref-and-the-dom/) |
| useState | คืนค่าปัจจุบันของ render รอบนี้ พร้อม setter ที่สั่ง re-render ด้วยค่าใหม่ — มันไม่เคย mutate snapshot ตรง ๆ เลย และ argument ของ setter จะถูกประเมินเป็น lazy initializer function เฉพาะ render แรกสุดเท่านั้น | [useState & Updates](/react/th/hooks/usestate-and-updates/) |
| useSyncExternalStore | subscribe component เข้ากับ store ที่อยู่นอก React (global variable, browser API, library อย่าง Redux) โดยไม่เกิด tearing ให้ทุก consumer ได้ snapshot ที่สอดคล้องกันหนึ่งชุดต่อ render — `getSnapshot` ต้องคืนค่า primitive หรือ reference ที่ cache ไว้ ไม่งั้น object ใหม่ทุกครั้งจะทำให้เกิด infinite loop จริง ๆ | [External Stores](/react/th/state-and-data/external-stores/) |
| useTransition | คืน `[isPending, startTransition]` — รูปแบบ hook ของการทำเครื่องหมายว่า update ไม่เร่งด่วน เวลาที่เราถือ state setter อยู่ตรงจุดเรียกเอง ถ้ามีแค่ค่า (เช่น prop) ที่ไม่มี setter ให้ห่อ ให้ใช้ `useDeferredValue` แทน | [Transitions](/react/th/concurrent-and-suspense/transitions/) |
