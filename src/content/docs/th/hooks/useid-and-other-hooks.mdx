## `useId`: id ที่ SSR-safe

`useId` สร้าง id string ที่ unique และ stable สำหรับ component instance หนึ่งตัว ถูกออกแบบมาโดยเฉพาะให้ตรงกันระหว่าง HTML ที่ render จาก server กับ hydration pass ฝั่ง client ซึ่ง counter ที่เขียนมือหรือ `Math.random()` การันตีแบบนี้ไม่ได้

```jsx
import { useId } from 'react';

function PasswordField() {
  const passwordHintId = useId();
  return (
    <>
      <label>
        Password:
        <input type="password" aria-describedby={passwordHintId} />
      </label>
      <p id={passwordHintId}>The password should contain at least 18 characters</p>
    </>
  );
}
```

การ hardcode id string ทำงานได้แค่กับ component instance เดียว render `PasswordField` สองครั้งแล้ว id ที่ hardcode ไว้จะชนกัน — HTML ผิด (id ซ้ำ) และการเชื่อม `aria-describedby` พัง เพราะ accessibility tree ของ browser เชื่อม id กับ element ได้แค่ตัวเดียว

```tsx
// src/__tests__/useid-duplicate-ids.test.tsx
import { useId } from 'react';
import { render, cleanup } from '@testing-library/react';
import { afterEach, expect, test } from 'vitest';

afterEach(cleanup);

// 🔴 Hardcoded id: every instance collides — invalid HTML (duplicate ids)
// and broken `aria-describedby` association for assistive tech.
function BadField() {
  return (
    <>
      <input aria-describedby="hint" />
      <p id="hint">Required</p>
    </>
  );
}

// ✅ useId: unique per component instance, stable across the component's life.
function GoodField() {
  const hintId = useId();
  return (
    <>
      <input aria-describedby={hintId} />
      <p id={hintId}>Required</p>
    </>
  );
}

test('hardcoded ids collide when a component renders more than once', () => {
  const { container } = render(
    <>
      <BadField />
      <BadField />
    </>,
  );
  const ids = [...container.querySelectorAll('p')].map((p) => p.id);
  expect(ids).toEqual(['hint', 'hint']); // duplicate — invalid HTML
});

test('useId gives each instance a distinct id', () => {
  const { container } = render(
    <>
      <GoodField />
      <GoodField />
    </>,
  );
  const ids = [...container.querySelectorAll('p')].map((p) => p.id);
  expect(new Set(ids).size).toBe(2); // no collision
});
```

```text
✓ hardcoded ids collide when a component renders more than once
✓ useId gives each instance a distinct id

Test Files  1 passed (1)
     Tests  2 passed (2)
```

ถ้า render **React app อิสระมากกว่าหนึ่งตัวในหน้าเดียวกัน** ให้ส่ง option `identifierPrefix` ให้ `createRoot`/`hydrateRoot` (และให้ตรงกันที่ `renderToPipeableStream` ฝั่ง server) เพื่อให้ id ของสอง app ชนกันไม่ได้เลย:

```js
const root1 = createRoot(document.getElementById('root1'), { identifierPrefix: 'app1-' });
const root2 = createRoot(document.getElementById('root2'), { identifierPrefix: 'app2-' });
```

**อย่า** ใช้ `useId` สร้าง key ให้ list — มันมีไว้สำหรับ accessibility attribute id บนจำนวน element ที่*คงที่*ต่อ component instance ไม่ใช่ identity ต่อ item ใน list ที่เปลี่ยนแปลงได้ (ใช้ data id ที่ stable ของแต่ละ item เองสำหรับกรณีนั้น)

## `useSyncExternalStore`: subscribe state ที่อยู่นอก React

เมื่อ state อยู่ใน store ที่ไม่ใช่ของ React เอง (global variable, browser API, library อย่าง Redux หรือ subscription model ข้างใต้ Zustand) `useSyncExternalStore` คือ hook ที่ subscribe component เข้ากับมันอย่างถูกต้อง — รวมถึง `getServerSnapshot` สำหรับ SSR และการป้องกัน "tearing" (component ต่างกันเห็น value ต่างกันจาก store เดียวกันใน render เดียว) บทพี่น้องในโมดูลนี้ [External Stores](/react/th/state-and-data/external-stores/) ครอบคลุม API เต็ม, ปัญหา tearing และ selector pitfall คลาสสิกแบบละเอียด — นี่คือย่อหน้าเดียวที่ชี้ทาง ไม่ใช่การพูดซ้ำ

## `useDeferredValue`: `initialValue` สำหรับ render แรก (React 19)

`useDeferredValue` ให้ส่วนที่แพงของ UI ล้าหลังการอัปเดตที่ urgent แทนที่จะบล็อกมัน ตั้งแต่ React 19 มันรับ argument ที่สอง `initialValue` ใช้แค่ตอน render **แรก** ของ component เท่านั้น:

```jsx
import { useState, useDeferredValue } from 'react';

function SearchPage() {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query, ''); // '' only on first render
  // ...
}
```

ถ้าไม่มี `initialValue` react.dev บอกตรง ๆ ว่า hook "will not defer during the initial render" — render แรกจะได้ `value` ตรง ๆ เลย ถ้ามีมัน render แรกจะได้ `initialValue` แทน ทำให้แสดง placeholder ทันทีก่อนที่จะพิมพ์ query จริงเลยด้วยซ้ำ

```tsx
// src/__tests__/useid-and-other-hooks.test.tsx (excerpt)
test('useDeferredValue(value, initialValue) uses initialValue on the FIRST render, not a deferred empty value', () => {
  const seenOnFirstRender: string[] = [];
  function Search({ query }: { query: string }) {
    const deferred = useDeferredValue(query, 'placeholder');
    seenOnFirstRender.push(deferred);
    return <output>{deferred}</output>;
  }
  render(<Search query="hello" />);
  // react.dev: "During the initial render, the returned deferred value will
  // be initialValue... If omitted, useDeferredValue will not defer during
  // the initial render." The first render shows the placeholder, not 'hello'.
  expect(seenOnFirstRender[0]).toBe('placeholder');
});
```

## `useDebugValue`: ติด label ให้ custom hook ใน DevTools

`useDebugValue` ไม่เพิ่มพฤติกรรม runtime อะไรเลย — มันมีไว้แค่ให้ React DevTools โชว์ label ที่อ่านง่ายข้าง state ของ custom hook แทนที่จะเป็น list ของ raw value ที่อ่านไม่รู้เรื่อง:

```jsx
function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(true);
  // ...
  useDebugValue(isOnline ? 'Online' : 'Offline');
  return isOnline;
}
```

สำหรับ value ที่ format เป็น string ที่อ่านง่ายแล้วแพง ให้ส่ง function `format` ตัวที่สอง — React จะเรียกมันแค่ตอนที่ DevTools กำลัง inspect hook นั้นจริง ๆ ไม่ใช่ทุก render:

```jsx
useDebugValue(date, (d) => d.toDateString());
```

คุณจะเรียกอันนี้แค่จากใน custom hook ที่คุณ**เขียนเอง**เท่านั้น — มันไม่มีอะไรให้เพิ่มในตัว component ธรรมดา

## `useInsertionEffect`: สำหรับคนเขียน CSS-in-JS เท่านั้น

`useInsertionEffect` ยิง**ก่อน**ทุก layout effect โดยเฉพาะเพื่อให้ CSS-in-JS library inject `<style>` tag เข้า DOM ก่อนที่ `useLayoutEffect` ของ component คุณจะพยายามอ่าน layout ที่ขึ้นกับ style เหล่านั้น พิสูจน์ด้านล่างเทียบกับ `useLayoutEffect`:

```tsx
// src/__tests__/useid-and-other-hooks.test.tsx (excerpt)
test('useInsertionEffect fires before useLayoutEffect', () => {
  const log: string[] = [];
  function Widget() {
    useInsertionEffect(() => {
      log.push('insertion');
    });
    useLayoutEffect(() => {
      log.push('layout');
    });
    return null;
  }
  render(<Widget />);
  expect(log).toEqual(['insertion', 'layout']);
});
```

```text
✓ useInsertionEffect fires before useLayoutEffect

Test Files  1 passed (1)
     Tests  1 passed (1)
```

react.dev พูดตรงกลุ่มเป้าหมายชัดเจน: hook นี้ "primarily intended for CSS-in-JS library authors" มันยังมาพร้อม caveat ที่คมมาก — update state จากในนั้นไม่ได้, ref ยังไม่ attach ตอนมันรัน และรันแค่ฝั่ง client เท่านั้น application code ควรใช้ `useEffect` หรือ `useLayoutEffect` แทน ถ้าคุณไม่ได้กำลังสร้าง styling library คุณแทบไม่ต้องใช้ `useInsertionEffect` เลย

## Mental Model

ห้า hook นี้ไม่ใช่ของกองรวมแบบสุ่ม — แต่ละตัวมีอยู่เพราะมีขอบเขต*จำเพาะ*ที่ต้องข้าม ซึ่ง hook หลัก (`useState`, `useEffect`, `useRef`) ไม่ได้ถูกออกแบบมาสำหรับมัน: `useId` ข้ามขอบเขต server/client สำหรับการสร้าง identifier, `useSyncExternalStore` ข้ามขอบเขต React/non-React state, `useDeferredValue` ข้ามขอบเขต priority ของ rendering แบบ urgent/non-urgent, `useInsertionEffect` ข้ามขอบเขตเวลา styles-ก่อน-layout และ `useDebugValue` ข้ามขอบเขต runtime/การ inspect ของ DevTools ถ้าคุณไม่ได้ยืนอยู่ที่หนึ่งในห้าขอบเขตนี้ คุณไม่ต้องใช้ hook นั้น

## ข้อแลกเปลี่ยน

| Hook | ประโยชน์ | ต้นทุน |
| --- | --- | --- |
| `useId` | การันตีไม่มี id ชนกันข้าม instance หรือข้าม server/client hydration | เรียก hook เพิ่มอีกตัวสำหรับสิ่งที่ hardcoded string "ดูเหมือน" ทำแทนได้ |
| `useSyncExternalStore` | subscription ที่ถูกต้อง ไม่ tear กับ state นอก React พร้อม SSR support | setup มากกว่าการอ่าน global variable ตรง ๆ (แต่ความตรงนั้นแหละคือสาเหตุของ tearing) |
| `useDeferredValue(value, initialValue)` | first paint ที่ทันทีและสมเหตุสมผลก่อนที่ deferring จะเริ่มทำงาน | ต้องจำ argument เพิ่มอีกตัว มีผลแค่ render แรกเท่านั้น |
| `useInsertionEffect` | style มาถึงก่อนที่ layout effect จะอ่านมัน | มีประโยชน์แค่ใน styling library เป็น tool ที่ผิดสำหรับ effect ของ app ทั่วไป |

## ความเข้าใจผิดที่พบบ่อย

- **"hardcoded id string โอเคตราบใดที่ render component แค่ครั้งเดียว"** จริงจนกว่าจะมีคน reuse component ครั้งที่สองในหน้าเดียวกัน — พิสูจน์แล้วด้านบน นั่นคือการชนกันแบบ HTML ผิดทันที
- **"`useId` มีไว้สำหรับ React key ใน list"** ไม่ใช่ — มันมีไว้สำหรับ accessibility attribute id บนชุด element ที่คงที่ต่อ instance list key ต้องการ identity ต่อ item ตาม data ไม่ใช่ `useId`
- **"`useDeferredValue` ที่ไม่มี `initialValue` ก็ยัง defer ตอน render แรกเหมือนกัน"** react.dev บอกตรงข้าม: ถ้าไม่มี `initialValue` hook จะไม่ defer เลยใน render แรกนั้น — มันเริ่ม defer แค่ตอนอัปเดตครั้งถัดไป
- **"`useInsertionEffect` ก็แค่ `useEffect` ที่เร็วกว่าสำหรับใช้งานทั่วไป"** มันเป็น tool แคบสำหรับ style injection ที่มีข้อจำกัดจริง (update state ไม่ได้, ref ยังไม่ attach) — หยิบมาใช้ใน application code ทั่วไปแทบจะผิดเสมอ

## อ่านโค้ดที่ AI เขียน

เมื่อ code ที่ generate มาใช้ (หรือควรใช้แต่ไม่ใช้) hook เล็ก ๆ เหล่านี้ ให้เช็กสิ่งเหล่านี้ก่อนเชื่อมัน:

- accessibility id (`aria-describedby`, คู่ `htmlFor`/`id`) ถูก hardcode เป็น string literal แทนที่จะ generate ด้วย `useId` หรือเปล่า?
- `useId` ถูกใช้ key list ที่ render ด้วย `.map()` แทนที่จะใช้ identifier ที่ stable ของแต่ละ item เองหรือเปล่า?
- component อ่านจาก external store (module-level variable, `window`, library ที่ไม่ใช่ React) ตรง ๆ ระหว่าง render แทนที่จะผ่าน `useSyncExternalStore` เสี่ยง tearing หรือ mismatch ระหว่าง server/client หรือเปล่า?
- `useDeferredValue` ถูกใช้โดยไม่ได้พิจารณาว่า render แรกควรโชว์ `initialValue` หรือ value จริงทันทีหรือเปล่า?
- `useInsertionEffect` ถูกใช้ทำอะไรที่ไม่ใช่ style injection — สัญญาณว่าผู้เขียนหยิบมันมาโดยไม่เข้าใจจุดประสงค์และข้อจำกัดที่แคบของมันหรือเปล่า?
